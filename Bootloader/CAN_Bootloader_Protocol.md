# CAN Bootloader Protocol (F280039C)

Документ описывает фактический протокол обмена между PC-программатором и CAN bootloader на MCU.

## 1. Участники и роли

- **PC (WinForms, `Stepulyov/ASt_MainF.cs`)**
  - отправляет команды и данные прошивки
  - ждёт ACK/статусы от MCU
- **MCU bootloader (`3ph_Inverter/Bootloader/can_bootloader.c`)**
  - принимает команды
  - стирает FLASH
  - программирует блоки
  - проверяет checksum
  - передаёт управление приложению

## 2. CAN IDs и формат кадров

См. `can_boot_protocol.h`:

- **MCU -> PC**: `BOOT_CAN_TX_ID = 0x32`
- **PC -> MCU**: `BOOT_CAN_RX_ID = 0x33`

Кадры — standard 11-bit ID, DLC=8.

Скорость канала в текущей рабочей конфигурации: **1 Мбит/с** (и в UI, и в bootloader-сессии).

Практически команды/ответы кодируются как 16-битное слово в `DATA[0..1]` (little-endian), остальные байты обычно 0.
* little-endian — это порядок байт, где младший байт идёт первым.
Исключение: заголовок загрузки после `CMD_LOAD` передаётся одним 8-байтным кадром (4 слова подряд).
 

- Отправка слова из PC: `Send_33(ushort)`
- Приём слова на PC: `Read_32()`
- Отправка слова из MCU: `boot_can_send_word(uint16_t)`
- Приём слова на MCU: `boot_can_recv_word()` / `boot_can_recv_word_blocking()`

## 3. Последовательность фаз (state machine)

## 3.1 Handshake

1. PC шлёт `CMD_HANDSHAKE (0xCC01)` циклически.
2. MCU в цикле ждёт это слово.
3. MCU отвечает `ACK_HANDSHAKE (0x02CC)`.

Только после этого переход к erase.

## 3.2 Erase

1. PC шлёт `CMD_ERASE (0xCC02)`.
2. MCU начинает стирание банков/секторов приложения.
3. MCU шлёт статусы прогресса (ID `0x32`):
   - `0xEE01`, `0xEE00`, `0xEE02` — диагностические маркеры
   - `0xEB0s` — Bank0 sector `s`
   - `0xEB1s` — Bank1 sector `s`
   - `0xEB2s` — Bank2 sector `s`
4. При ошибках таймаута FSM MCU шлёт: `0xD0nn/0xD1nn/0xD2nn`.

   Где **FSM** = **Flash State Machine** (внутренний автомат контроллера FLASH),
   который выполняет операции стирания/программирования и сигнализирует готовность.

   Подробно по формату:

   - `0xD0nn` -> timeout при стирании сектора в **Bank0**
   - `0xD1nn` -> timeout при стирании сектора в **Bank1**
   - `0xD2nn` -> timeout при стирании сектора в **Bank2**

   Где:

   - старший байт (`0xD0/0xD1/0xD2`) кодирует номер банка
   - младший байт `nn` кодирует индекс сектора, на котором зафиксирован timeout ожидания готовности FSM

   Источник в коде MCU:

   - маркер формируется в `boot_wait_fsm_ready(timeoutWord)`
   - в `bootloader_erase_app_flash()` в функцию передаётся:
     - Bank0: `0xD000 | sector`
     - Bank1: `0xD100 | sector`
     - Bank2: `0xD200 | sector`

   Примеры:

   - `0xD00A` -> timeout FSM на Bank0, Sector10
   - `0xD105` -> timeout FSM на Bank1, Sector5
   - `0xD20F` -> timeout FSM на Bank2, Sector15

   Что это означает по сути:

   - команда `Fapi_issueAsyncCommandWithAddress(Fapi_EraseSector, ...)` была принята,
   - но `Fapi_checkFsmForReady()` не вернул готовность в отведённое окно ожидания,
   - bootloader сообщает конкретный банк/сектор и завершает фазу erase с ошибкой.
   - после отправки кода ошибки загрузчик ждёт подтверждение от PC (`CMD_ERROR_RECEIVED`), затем делает reset.
   - если подтверждение не пришло за таймаут ожидания подтверждения, загрузчик всё равно делает reset.

   > Примечание (простыми словами):
   >
   > - **FSM** — это аппаратный блок внутри MCU (**Flash State Machine**), который реально стирает/программирует FLASH.
   > - **FAPI** — это программная библиотека/интерфейс, через который код управляет этим аппаратным FSM.
   > - Поэтому длинные функции `Fapi_*` — это не "сам FSM", а команды/проверки для работы с ним.

   Рекомендуемая обработка на PC:

   - немедленно прекращать цикл erase,
   - показывать диагностическое сообщение с bank/sector,
   - не переходить к `CMD_LOAD`.
5. После успешного erase MCU шлёт `ACK_ERASE (0x05CC)`.

PC в это время в цикле читает статусы прогресса `Read_32()` до `0x05CC`, показывая прогресс erase.

## 3.3 Load header (переход к загрузке)

1. После получения `0x05CC` PC отправляет:
   - кадр 1: `CMD_LOAD (0xCC07)`
   - кадр 2 (8 байт): `addrHi`, `addrLo`, `sizeHi`, `sizeLo`
2. MCU ждёт `CMD_LOAD`, затем блокирующе принимает 8-байтный кадр заголовка.

   Практическое правило для PC в текущей реализации (подтверждено тестом):

   - между отправкой `CMD_LOAD` и кадром header нужна короткая пауза порядка **3 ms**;
   - при отсутствии первого `ACK_BLOCK (0x06CC)` допустимо повторить пару
     `CMD_LOAD + header` (до нескольких попыток).

   Наблюдаемый симптом при слишком плотной отправке без паузы:

   - MCU продолжает слать `ACK_ERASE (0x05CC)` и не переходит в data-phase.

   Формат кадра 2 (`DLC=8`, little-endian слова):

   - bytes `[0..1]` -> `addrHi`
   - bytes `[2..3]` -> `addrLo`
   - bytes `[4..5]` -> `sizeHi`
   - bytes `[6..7]` -> `sizeLo`

Важно: это самая чувствительная точка протокола.

### 3.3.1 Предлагаемое ужесточение handshake для `CMD_LOAD`

В проекте действует практическое правило: **каждая команда PC должна подтверждаться ACK от MCU**.

Предложение для следующей ревизии протокола:

1. PC отправляет `CMD_LOAD (0xCC07)`.
2. MCU сразу отвечает отдельным ACK (логично использовать `ACK_LOAD` как «готов к header/data»).
3. Только после этого PC отправляет header и data-блоки.

Ожидаемый эффект:

- убрать зависимость от фиксированной паузы ~3 ms между `CMD_LOAD` и header,
- сделать фазу перехода `erase -> load` симметричной остальным фазам с явным подтверждением.

Примечание: сейчас это **архитектурное предложение**; текущая реализация остаётся совместимой с действующим алгоритмом (пауза + ретраи).

## 3.4 Передача данных (program)

1. MCU переходит в режим ожидания первого data-блока и периодически шлёт `ACK_BLOCK (0x06CC)`.
2. PC ждёт первый `0x06CC` (в UI в этот момент видно `Загрузка...0%`).
3. PC отправляет данные блоками по 8 байт (DLC=8, ID=0x33).
4. MCU на каждый блок:
   - принимает 8 байт
   - программирует FLASH (64 бита)
   - шлёт `ACK_BLOCK (0x06CC)`
5. PC после каждого блока ждёт `0x06CC`.

Коды ошибок программирования:

- `0xDFxx` — код статуса Fapi
- `0xDEAD` — фатальная ошибка

## 3.5 Завершение загрузки и verify

1. После последнего блока MCU шлёт `ACK_LOAD (0x07CC)` (повторно, пока не придёт verify).
2. PC шлёт `CMD_VERIFY (0xCC08)`.
3. MCU отвечает `ACK_VERIFY_READY (0x09CC)`.
4. PC шлёт checksum (2 слова).
5. MCU сравнивает и шлёт:
   - `ACK_VERIFY (0x08CC)` при успехе
   - reset при несовпадении.

## 3.6 Reboot / jump

1. PC шлёт `CMD_REBOOT (0xFE17)`.
2. MCU шлёт `ACK_REBOOT_READY (0x17FE)`.
3. PC шлёт `entryHi/entryLo`.
4. MCU шлёт `ACK_REBOOT (0x18FE)`.
5. MCU делает `boot_jump_to_app(entryAddr)`.

## 3.7 FAPI-функции простыми словами

Ниже краткая «шпаргалка» по основным вызовам `Fapi_*`, используемым в загрузчике:

- `Fapi_initializeAPI(...)`
  - «Включи библиотеку Flash API и подготовь её к работе».
- `Fapi_setActiveFlashBank(bank)`
  - «Выбери, с каким банком FLASH сейчас работаем (Bank0/1/2)».
- `Fapi_setupBankSectorEnable()`
  - «Разреши операции по секторам выбранного банка».
- `Fapi_issueAsyncCommandWithAddress(Fapi_EraseSector, addr)`
  - «Запусти стирание сектора по адресу `addr`».
- `Fapi_checkFsmForReady()`
  - «Проверь, закончил ли аппаратный FLASH-движок (FSM) операцию».
- `Fapi_getFsmStatus()`
  - «Получи итог: успех или код ошибки после операции».
- `Fapi_issueProgrammingCommand(addr, data, ...)`
  - «Запиши данные во FLASH по адресу `addr`».

## 3.8 Подтверждение ошибки перед reset

Для диагностических ошибок MCU использует дополнительное подтверждение от PC:

- PC -> MCU: `CMD_ERROR_RECEIVED (0xCC0E)`

Поток для ошибок erase/program:

1. MCU отправляет код ошибки (`0xD0nn/0xD1nn/0xD2nn`, `0xDFxx` или `0xDEAD`).
2. PC, получив код, отправляет `CMD_ERROR_RECEIVED`.
3. MCU получает подтверждение и выполняет reset.
4. Если подтверждение не пришло в окно ожидания, MCU выполняет reset по таймауту.

## 4. Ограничения FLASH и errata

В `bootloader_program_block()`:

- Для F280039C учтена errata: последние 16 слов Bank2 (`0x0AFFF0..0x0AFFFF`) **не программируются**.
- Эти байты остаются `0xFF`, при этом checksum на PC/MCU считается согласованно.

Область приложения:

- start: `0x082000` (Bank0 Sec2)
- end: `0x0AFFFF`

Область bootloader (Sec0-1) не стирается и не программируется.

## 5. Тайминги и таймауты

Ключевые ожидания на MCU реализованы через `boot_delay_stub(100)` в цикле.

Назначение таймаутов на MCU:

- не допустить вечного зависания при потере CAN-кадров или аппаратной ошибке FLASH,
- завершить ошибочную сессию предсказуемо,
- выполнить reset и вернуть систему в известное состояние.

Ключевые ожидания на PC:

- handshake loop
- erase loop
- waiting `0x06CC` at 0%
- per-block ACK wait
- verify/reboot ACK wait

Ориентиры по окнам ожидания в текущем коде PC (`Bootloader.cs`):

- handshake: до ~30 с (`3000 * 10 ms`),
- erase: до ~10 мин (`60000 * 10 ms`),
- ожидание первого/каждого ACK блока: до ~30 с,
- verify/reboot ACK: до ~30 с на фазу.

Любые лишние задержки на PC в `Read_32()` (например ожидание события при неактивном receive worker) приводят к рассинхронизации фаз.

## 6. Где обычно зависает и что это значит

## 6.1 UI: `Загрузка...0%`

PC уже отправил `CMD_LOAD + header` и ждёт первый `ACK_BLOCK (0x06CC)`.

Причины:

- MCU не получил `CMD_LOAD` (застрял в фазе ожидания команды загрузки)
- MCU получил `CMD_LOAD`, но не получил первый data-блок
- потеря/гонка кадров на PC между фоновым `_crw` и worker загрузчика

## 6.2 Стек MCU в `bootloader_main` около цикла ожидания `CMD_LOAD`

- это фаза 3 (между erase и program)
- `debug_byteCount == 0` ожидаемо
- означает, что до data-фазы MCU не дошёл

## 6.3 Стек MCU в первом ожидании data-блока (first block wait)

- `CMD_LOAD` уже принят
- заголовок принят
- MCU ждёт первый data CAN кадр

## 7. Наблюдаемые инварианты (для диагностики)

При нормальной сессии порядок ответов MCU (сокращённо):

1. `0x02CC`
2. `... erase markers ...`
3. `0x05CC`
4. `0x06CC` (готов к первому блоку)
5. `0x06CC` на каждый блок
6. `0x07CC`
7. `0x09CC`
8. `0x08CC`
9. `0x17FE`
10. `0x18FE`

Если порядок ломается — проблема транспорт/синхронизация, а не формат бинарника.

## 8. Правила для реализации PC-части (чтобы не ломать протокол)

1. На время прошивки должен быть **один владелец чтения CAN**.
2. Нельзя иметь 300ms задержку на каждый `Read_32()` в фазах erase/load/program.
3. После завершения прошивки нужно корректно освободить bootloader handle и заново подключить UI-канал.
4. Все команды bootloader отправлять с ID `0x33`, DLC=8.
5. Все ответы ждать по ID `0x32`.

## 9. Коды команд/ACK (краткая таблица)

- `CMD_HANDSHAKE = 0xCC01`
- `ACK_HANDSHAKE = 0x02CC`
- `CMD_ERASE = 0xCC02`
- `CMD_ERROR_RECEIVED = 0xCC0E`
- `ACK_ERASE = 0x05CC`
- `CMD_LOAD = 0xCC07`
- `ACK_BLOCK = 0x06CC`
- `ACK_LOAD = 0x07CC`
- `CMD_VERIFY = 0xCC08`
- `ACK_VERIFY_READY = 0x09CC`
- `ACK_VERIFY = 0x08CC`
- `CMD_REBOOT = 0xFE17`
- `ACK_REBOOT_READY = 0x17FE`
- `ACK_REBOOT = 0x18FE`

### 9.1 Предложенные коды для v2 (ускорение с ACK-пакетами)

Ниже — предложение, чтобы не ломать существующие коды и сохранить обратную совместимость.

- `ACK_LOAD_READY = 0x0ACC`
  - MCU подтверждает, что `CMD_LOAD` принят и можно отправлять header.
- `CMD_SET_CHUNK = 0xCC0A`
  - PC сообщает размер пакета в блоках (например, `16` или `32`).
- `ACK_SET_CHUNK = 0x0BCC`
  - MCU принял параметр размера пакета.
- `ACK_CHUNK = 0x0CCC`
  - MCU подтверждает успешную запись пакета (`chunkSeq` передаётся в payload).
- `NACK_CHUNK = 0x0DCC`
  - MCU сообщает ошибку пакета (`chunkSeq` + код причины в payload).
- `CMD_RETRY_CHUNK = 0xCC0D`
  - PC повторно отправляет пакет с указанным `chunkSeq`.

Примечания по payload (DLC=8):

- для `ACK_CHUNK`/`NACK_CHUNK`: `DATA[0..1] = ackWord`, `DATA[2..3] = chunkSeq`, `DATA[4..5] = errCode/0`, остальные `0`.
- для `CMD_SET_CHUNK`: `DATA[2..3] = blocksPerChunk` (кол-во 8-байтных блоков в пакете).

Режим совместимости:

- если MCU не поддерживает `ACK_LOAD_READY`/`ACK_SET_CHUNK`, PC откатывается на текущий режим (`ACK_BLOCK` на каждый блок).

## 10. Мини-чеклист при регрессии "второй Update CCS"

1. Убедиться, что `_crw` не конкурирует с `FlWrk_DoWork` за чтение CAN.
2. Проверить, что `Read_32()` не ждёт событие, когда `_crw` остановлен.
3. Проверить, что после прошивки PC делает clean reinit USB-CAN для UI.
4. Снять CAN trace ID `0x32/0x33` и сравнить с expected sequence из раздела 7.
5. Проверить MCU стек:
   - в ожидании `CMD_LOAD` или
   - в ожидании первого блока данных.

## 11. План ускорения bootloader без потери надёжности (v2)

### 11.1 Зафиксированная база (из текущих замеров)

- Пример измерения PC: `total=36564ms`, `load=32632ms`, `blocks=37994`, `avgAck≈833us`, `avgWrite≈25us`, `speed≈9.1KB/s`.
- Вывод: узкое место — ожидание ACK на каждый 8-байтный блок, а не отправка кадра PC.

### 11.2 Шаг A — строгий ACK для `CMD_LOAD`

Цель: убрать зависимость от паузы `~3 ms` и сделать фазы симметричными.

Предлагаемый поток:

1. PC -> MCU: `CMD_LOAD`
2. MCU -> PC: `ACK_LOAD_READY` (новый код ACK, отдельный от `ACK_LOAD` завершения)
3. PC -> MCU: header
4. MCU -> PC: `ACK_BLOCK` (готов к первому data-блоку)

Совместимость:

- На переходный период PC поддерживает оба варианта: новый (`ACK_LOAD_READY`) и старый (текущий flow с fallback).

### 11.3 Шаг B — пакетный ACK вместо ACK на каждый блок

Цель: кратно уменьшить накладные round-trip задержки.

Предлагаемый режим:

- MCU принимает и программирует данные по 8 байт, но подтверждает не каждый блок, а пакет из `N` блоков.
- Рекомендуемо начать с `N=16`, затем увеличить до `N=32`.
- ACK содержит номер пакета (`chunkSeq`).

### 11.4 Шаг C — контроль целостности пакета

Чтобы не терять надёжность:

- добавить `CRC16/CRC32` на пакет (`chunk`),
- при ошибке MCU шлёт `NACK_CHUNK(chunkSeq)`,
- PC повторяет только проблемный пакет.

Финальная проверка полного образа (`CMD_VERIFY` + checksum) сохраняется.

### 11.5 Рекомендуемое внедрение по релизам

1. `Release 1`: `ACK_LOAD_READY` + fallback совместимость на PC.
2. `Release 2`: `ACK per chunk (N=16)` + `chunkSeq`.
3. `Release 3`: `N=32` (если стабильно) + `CRC`/`NACK_CHUNK`.

### 11.6 Ожидаемый эффект

- При текущем профиле (`avgAck ~0.83 ms/8 bytes`) узкое место протокольное.
- Переход на ACK раз в 16-32 блока обычно даёт ускорение порядка 2-5x при сохранении надёжности (ACK на команды + CRC/повтор пакета).

## 12. State machine v2 (предлагаемая реализация)

### 12.1 Подготовка параметров передачи

1. PC -> MCU: `CMD_LOAD`
2. MCU -> PC: `ACK_LOAD_READY`
3. PC -> MCU: `CMD_SET_CHUNK` + `blocksPerChunk`
4. MCU -> PC: `ACK_SET_CHUNK`
5. PC -> MCU: header (`addrHi/addrLo/sizeHi/sizeLo`)
6. MCU -> PC: `ACK_BLOCK` (готов к приёму первого пакета)

Если `ACK_LOAD_READY`/`ACK_SET_CHUNK` не получены в окно ожидания, PC переключается в legacy-режим (текущий алгоритм).

### 12.2 Передача пакета (`chunkSeq`)

Пакет = `N` блоков по 8 байт (рекомендуемо `N=16` на первом этапе).

1. PC отправляет подряд `N` data-кадров (`ID=0x33`, `DLC=8`).
2. MCU программирует каждый 8-байтный блок во flash.
3. MCU считает CRC пакета в том же порядке, что и PC.
4. По завершении пакета MCU отправляет:
   - `ACK_CHUNK(chunkSeq)` при успехе,
   - `NACK_CHUNK(chunkSeq, errCode)` при ошибке.
5. При `NACK_CHUNK` PC повторяет только этот пакет (через `CMD_RETRY_CHUNK` или немедленный resend по `chunkSeq`).

### 12.3 Завершение передачи

1. После последнего подтверждённого пакета MCU -> PC: `ACK_LOAD`.
2. Далее фаза `CMD_VERIFY`/checksum остаётся как в v1.
3. Фаза `CMD_REBOOT` остаётся как в v1.

### 12.4 Таймауты и поведение при ошибках (v2)

- Таймаут `ACK_LOAD_READY`: короткое окно (например, 1-3 с), затем fallback на v1.
- Таймаут `ACK_SET_CHUNK`: короткое окно (1-3 с), затем fallback на v1.
- Таймаут `ACK_CHUNK`: окно рассчитывается из `N * tprog_block + запас`.
- Лимит повторов на один пакет: 3 попытки; затем аварийный выход с `CMD_ERROR_RECEIVED`.

### 12.5 Инварианты v2 для диагностики

Нормальный порядок после erase:

1. `ACK_ERASE`
2. `ACK_LOAD_READY`
3. `ACK_SET_CHUNK`
4. `ACK_BLOCK` (старт data-phase)
5. `ACK_CHUNK(seq=0..k)` / редкие `NACK_CHUNK`
6. `ACK_LOAD`
7. `ACK_VERIFY_READY`
8. `ACK_VERIFY`
9. `ACK_REBOOT_READY`
10. `ACK_REBOOT`
