# Протокол CAN-загрузчика F280039C

## Общая схема

```
┌─────────────┐     CAN 1Mbit/s     ┌─────────────┐
│   SHARP     │◄──────────────────►│   F280039C  │
│  (Windows)  │   ID=0x33 (TX)     │    (MCU)    │
│  Form1.cs   │   ID=0x32 (RX)     │  Bootloader │
└─────────────┘                    └─────────────┘
```

**Два участника:**
- **SHARP** — приложение на C# (Windows), файлы `MainWindow.cs` и `ASt_MainF.cs`
- **MCU** — микроконтроллер TI F280039C, файлы `can_bootloader.c`, `app_boot_request.c`

---

## Фаза 1: Подготовка (SHARP → MCU по рабочему каналу)

### Шаг 1.1 — Пользователь нажимает "Обновить прошивку"
**Файл:** `MainWindow.cs` → `updateFlashToolStripMenuItem_Click()`

```
Пользователь нажимает кнопку меню "Обновить прошивку"
│
├── Проверка: CAN подключён? (tsmConnect.Text == "Отключить")
│   Если нет → выход
│
├── Сохраняем номер CAN-канала: savedCh = Ch
│
├── Отправляем команду 9999 по рабочему протоколу (CAN ID=2, скорость 1 Мбит/с)
│   SendCanCommand(9999, skipConnectionCheck: true)
│
├── Ждём 200 мс (MCU переинициализирует CAN на 250K)
│
├── Отключаем UI (disconnect_CAN) — только интерфейс, без команды 3!
│
└── Вызываем Obl(savedCh) → открываем диалог выбора .out файла
```

### Шаг 1.2 — MCU получает команду 9999
**Файл:** `MBOX28.c` → `case 9999`

```
CAN-прерывание получает команду 9999
│
└── Вызывает app_request_firmware_update()
```

### Шаг 1.3 — Прямой переход в загрузчик (без перезагрузки)
**Файл:** `app_boot_request.c` → `app_request_firmware_update()`

> ⚠️ Функция выполняется из RAM (#pragma CODE_SECTION → .TI.ramfunc)

```
app_request_firmware_update()
│
├── IGBT1_Disable(), IGBT2_Disable() — безопасность силовой части
│
├── DINT — отключаем все прерывания
│
└── bootloader_main() — прямой переход в загрузчик
    │  Код загрузчика уже в RAM (.TI.ramfunc скопирован при старте)
    │  bootloader_main() переинициализирует CAN на 250K
    └── Не возвращается — в конце делает SysCtl_resetDevice()
```

**Почему НЕ нужна перезагрузка:**
- Код загрузчика уже в RAM (скопирован `Board_init()` при старте)
- `boot_can_init()` полностью переинициализирует CAN модуль
- IGBT отключены → силовая часть безопасна
- Прерывания запрещены → ничего не мешает

## Фаза 3: Обмен данными (SHARP ↔ MCU, CAN 250 Кбит/с)

### Шаг 3.0 — SHARP готовится к загрузке
**Файл:** `ASt_MainF.cs` → `Obl()` и `FlWrk_DoWork()`

```
Obl(savedCh):
│

├── CanaDisconnect() — освобождаем PCAN адаптер
│   └── PCANBasic.Uninitialize(Ch)
│
└── Показываем диалог выбора .out файла
    └── После выбора файла → _flWrk.RunWorkerAsync()
        └── Запускается FlWrk_DoWork() в фоновом потоке
```

**Файл:** `ASt_MainF.cs` → `FlWrk_DoWork()`

│
├── Конвертация .out → .bin (метод Cnv2)

## Адреса и константы

| Константа | Значение | Описание |
|-----------|----------|----------|
| `BOOT_CAN_TX_ID` | `0x64` | CAN ID ответов загрузчика (MCU → PC) |
| `BOOT_CAN_RX_ID` | `0x65` | CAN ID команд от SHARP (PC → MCU) |
| `APP_START_ADDR` | `0x082000` | Начало области приложения (Bank0 Sec2) |
| `APP_END_ADDR` | `0x0AFFFF` | Конец flash (Bank2 Sec15) |
| `FStartAddr` (C#) | `0x082000` | То же, на стороне SHARP |

## Скорости CAN

| Режим | Скорость | CAN ID TX→MCU | CAN ID MCU→PC |
|-------|----------|---------------|----------------|
| Рабочий | 1 Мбит/с | 2 | 1 |
| Загрузчик | 1 Мбит/с | 0x65 | 0x64 |

> Загрузчик работает на той же скорости 1 Мбит/с что и рабочий режим.
> Переинициализация PCAN адаптера не требуется.

## Типичные проблемы и решения

### 1. "Проверка связи..." зависает
**Причина:** MCU не вошёл в режим загрузчика.

Возможные причины:
- **CAN-фрейм с командой 9999 не дошёл** → проверить подключение
- **`app_request_firmware_update()` не в .TI.ramfunc** → проверить pragma
- **IGBT_Disable не определён** → проверить extern-декларации

### 2. "Ошибка загрузки" сразу после "CAN OK"
**Причина:** `PCANBasic.Initialize()` не может переинициализировать канал.

**Решение:** Проверить что `CanaDisconnect()` вызывается перед `FlWrk_DoWork()`.

## Приложение A — FAPI (краткая шпаргалка)

Ниже собраны функции Flash API, которые реально используются в загрузчике F280039C.

### `Fapi_initializeAPI(baseAddr, cpuFreqMHz)`
- Инициализирует библиотеку Flash API под текущую частоту CPU.
- Должна быть вызвана до erase/program операций.

### `Fapi_setActiveFlashBank(bank)`
- Выбирает активный flash-банк (`Bank0/Bank1/Bank2`).
- Перед переходом на другой банк вызывается повторно.

### `Fapi_setupBankSectorEnable()`
- Разрешает операции по секторам выбранного банка.

### `Fapi_issueAsyncCommandWithAddress(Fapi_EraseSector, addr)`
- Запускает стирание сектора по адресу `addr`.
- Команда асинхронная: завершение проверяется отдельно.

### `Fapi_checkFsmForReady()`
- Проверка готовности FSM (Flash State Machine).
- Пока `FsmBusy` — операция erase/program не завершена.

### `Fapi_getFsmStatus()`
- Чтение статуса FSM после завершения операции.
- При ошибке статус кодируется в диагностические слова (`0xD0nn`, `0xDFxx` и т.д.).

### `Fapi_issueProgrammingCommand(addr, data, byteCount, ... )`
- Программирует данные в flash по адресу `addr`.
- В нашем протоколе передача идёт блоками по 8 байт (64 бита).

## Приложение B — Зафиксированные коррекции протокола

Эти пункты отражают рабочие коррекции, согласованные в проекте.

1. **Единый владелец чтения CAN во время загрузки**
   - На период `FlWrk_DoWork()` фоновый `_crw` останавливается.
   - Это убирает гонки за входящие кадры bootloader (`ID=0x32`).

2. **`Read_32()` без искусственной задержки при остановленном `_crw`**
   - Если `_crw` не активен, чтение идёт напрямую из очереди/PCAN polling.
   - Устранена рассинхронизация фаз erase/load/program из-за лишнего ожидания.

3. **`CMD_LOAD + header` с короткой паузой**
   - Между `0xCC07` и 8-байтным header оставляется ~3 мс.
   - При отсутствии первого `ACK_BLOCK` допускается повтор пары.

4. **Передача данных блоками по 8 байт + ACK на каждый блок**
   - SHARP ждёт `0x06CC` после каждого блока.
   - Это исключает скрытую потерю кадров в data-phase.

5. **Обработка диагностических ошибок erase/program**
   - При `0xD0nn/0xD1nn/0xD2nn`, `0xDFxx`, `0xDEAD` загрузка останавливается.
   - SHARP отправляет `CMD_ERROR_RECEIVED (0xCC0E)`.

6. **Финальная синхронизация verify/reboot**
   - Проверяются все ACK: `0x09CC`, `0x08CC`, `0x17FE`, `0x18FE`.
   - После завершения SHARP корректно освобождает bootloader-handle и возвращает UI-режим.
