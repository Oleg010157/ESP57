K1 08.08.2026

Краткая аннотация нововведений:
- Разобран "перевёрнутый" эффект: при ВКЛЮЧЁННОЙ телеметрии квитирование выглядело идеальным
  (жёлтого нет нигде), при ВЫКЛЮЧЕННОЙ — жёлтый проскакивал при дёрганье трек-бара. Причина
  оказалась не в CAN и не в ACK, а в очереди сообщений UI-потока. Форсирована отрисовка
  значения NUD при протяжке ползунков Load/Gain.

Ключевое исправление версии:
- Присваивание BackColor/Value контролу делает только Invalidate(), не рисует. WM_PAINT в
  GetMessage стоит предпоследним по приоритету: ниже sent-сообщений, ниже posted-сообщений
  (сюда попадает Control.BeginInvoke) и ниже ввода мыши; ниже только WM_TIMER. Контрол при
  отрисовке рисует ТЕКУЩЕЕ состояние, а не историю присваиваний; повторные Invalidate
  сливаются в одну область.
  Идущая телеметрия непрерывно кладёт в очередь UI posted-сообщения (BeginInvoke на каждый
  кадр 140 из ProcessFrame100 -> U4_U5_Viewer и из ProcessFrame116) плюс meterTimer_Tick
  перезаписывает десятки лейблов живыми значениями. Очередь не пустеет -> до WM_PAINT поток
  не доходит -> промежуточные состояния контролов физически не рисуются.
  Отсюда обе "аномалии": жёлтый (живёт единицы мс между отправкой и ACK) не появлялся на
  экране ни разу, а цифра в NUD обновлялась рывками. Со связью и квитированием при этом всё
  было в порядке.

PC / WinForms (ICDIBasic):
- MainWindow.cs Tbar_Scroll(): после присваивания x.nud.Value добавлены x.nud.Refresh() и
  Update() по x.nud.Controls. Дочерний TextBox обновляется отдельно, т.к. UpdateWindow
  родителя на детей не распространяется, а цифра и фон NUD живут именно в этом дочернем
  контроле (BackColor родителя пробрасывается в него).
- Жёлтый оставлен как был: форсирование отрисовки в Tbar_Send было ВРЕМЕННЫМ, только для
  проверки гипотезы, и в коммит НЕ вошло. При протяжке жёлтый по-прежнему гасится очередью
  и глаза не мозолит — по решению пользователя это устраивает.

Диагностика (как проверялось):
- В Tbar_Send временно добавлен x.nud.Update() (синхронный WM_PAINT). Жёлтый сразу стал
  виден и с включённой телеметрией -> гипотеза об отрисовке подтверждена, строка удалена.
- Штатная альтернатива для точных замеров, если тема всплывёт снова: CAN-лог (Debug-сборка,
  CAN_LOG в Motor_Control.csproj, галка "CAN логирование"). Колонка TxRx_us = круговой путь
  по CAN, Rx13_Rx_us = задержка от прихода ACK в рабочий поток до обработки в UI-потоке,
  т.е. чистая задержка очереди UI. Разделяет "проблема в связи" и "проблема в UI" однозначно.

Почему жёлтого много при протяжке (не дефект, поведение по построению):
- Tbar_Send висит на ValueChanged, т.е. команда уходит на КАЖДЫЙ тик ползунка. Гашение в
  ccs_To_NUD срабатывает по условию x.tbar.Value == d1, т.е. эхо сравнивается с ТЕКУЩИМ
  положением ползунка. Промежуточные ACK приходят с устаревшим d1 и жёлтый не снимают;
  гасит только последний. Отсюда "иногда проскакивает" и ощущение запаздывания.

История вопроса:
- Раньше картина была обратной (жёлтый висел именно при включённой телеметрии): BeginInvoke
  слался на каждый кадр и забивал очередь настолько, что задерживалась и обработка ACK, и
  события трек-бара. Вылечено троттлингом _ract в Stepulyov/ASt_MainF.cs (1 раз на 10 кадров).
  После этого нагрузка на очередь упала до уровня, который ACK уже не задерживает, но
  промежуточную отрисовку всё ещё подавляет — отсюда и "переворот" симптома.

Риски / ограничения:
- Refresh()+Update() выполняются синхронно на каждый тик протяжки. Заметного утяжеления
  ползунка на стенде не выявлено, но при дальнейшем росте нагрузки на UI-поток это первое
  место, куда смотреть.

Открытые вопросы (на будущее, в этой версии не трогалось):
- Жёлтый несёт два разных смысла на одном визуальном канале: "жду квитанцию" (норма, живёт
  миллисекунды) и "рассогласование UI <-> MCU" (авария). Различить на экране нельзя, из-за
  чего настоящее расхождение может быть пропущено. Решение — развести каналы: транзиент в
  ForeColor/рамку, рассогласование в BackColor, и права владения не пересекаются.
- Сверка уставок по телеметрии покрывает только БИТЫ (mbit_check / sbit_check из
  ProcessFrame116). Значения — load, gain, RPM, Imax, ramp, режимы modeH/modeL — не
  мониторятся: mMode_check и mflag_check закомментированы в MainWindow.cs (~278-281),
  предположительно из-за коллизии с жёлтым от Tbar_Send (mflag_check пишет в тот же
  m.load.nud.BackColor). Данные для сверки в кадре 140 УЖЕ приходят и MCU трогать не надо:
  M1/M2.ccs.gain и flags — ProcessFrame109 (блок 5); umode -> modeH/modeL — ProcessFrame116
  case 0; speedRef/slipRef/slipMax — ProcessFrame116 case 3. Значения load в телеметрии нет,
  его пришлось бы добавлять на MCU.
- При включении такой сверки обязателен pending-таймаут (~300 мс): пока по контролу висит
  неотвеченная команда, сверку подавлять, по истечении — отдавать управление watchdog'у.
  Иначе при протяжке ползунка телеметрия отстаёт от уставки на цикл и watchdog будет
  срабатывать непрерывно.

Примечание:
- Статус проверки на стенде: подтверждено. Цифра в NUD при протяжке идёт плавно и с
  включённой телеметрией; жёлтый при протяжке не мешает. Сборка Debug: 0 ошибок,
  0 предупреждений.

K1 23.07.2026

Краткая аннотация нововведений:

Ключевое исправление версии:

  не выполнялся (счётчик пар вычислялся как 0). В UI все поля декодировались нулями (в т.ч.
  ProcessFrame116 не доходил до case 6), Controls оставались жёлтыми. Лечение: цикл переписан
  в прямую форму for(i=0; i<numWords; i+=2) + чистая пересборка/перепрошивка. Проверено на
  железе: payload заполняется, ECR=0.

MCU (INVERTOR_CCS):
- REF_Kadr.c send_REF_kadr(): убраны общие локальные d1..d4, каждый блок пишет НАПРЯМУЮ в
  tele[]. Исключён перенос "остатка" между блоками (латентный класс багов). Незаданные в
  конкретном case поля теперь 0 вместо мусора.
- myMCAN.c Send_mbox_FD: цикл упаковки 16-битных слов переписан в прямую форму (надёжнее по
  кодогенерации C28x, чем прежний вариант с pairs=(numWords+1)/2).

  остаток). Заготовки под реальные значения оставлены закомментированными на MCU.

PC / WinForms (ICDIBasic):
- Oleg/Kadr60.cs: убраны все [MethodImpl(AggressiveInlining)] у ProcessFrameXXX и лишний
  using CompilerServices — микрооптимизация без эффекта (JIT их всё равно не встраивал на
  функциях со switch/BeginInvoke). Осталась читаемая структура switch -> ProcessFrameXXX.

Примечание:
- Диагностика задержки ACK: измеренная задержка определяется планировщиком Windows и частотой
  CPU (спящий между командами ПК), а не CAN-шиной. Поэтому "одновременное" дёрганье двух моторов
  даёт МЕНЬШУЮ задержку, чем одиночное. Правки timeBeginPeriod/приоритет процесса были временными
  для проверки гипотезы и в коммит НЕ вошли.
- Статус проверки на стенде: Controls больше не остаются жёлтыми, данные приходят.

K1 22.07.2026

Краткая аннотация нововведений:
- Отлажена и стабилизирована связь CAN FD между MCU (F28P550SJ9, M_CAN) и ПК (PCAN-USB FD).
- Медленная телеметрия консолидирована из 8 отдельных 8-байтных кадров в ОДИН заполненный
  64-байтный CAN FD кадр (ID 140).

Ключевое исправление версии:
- 5 Мбит/с не работал: Bit1-ошибки в фазе данных (PSR: DLEC=4), TEC доходил до 128 (Error
  Passive). Узкое место — задержка петли трансивера (TCAN332, ~113 нс) на 200-нс бите, а не
  UI/PCAN/MCAN. Переход на 2.5 Мбит/с (1 Мбит арбитраж / 2.5 Мбит данные, SP ~75/77%,
  tdco=29) — ECR=0, связь устойчива.
- Исправлена карта TX-буфер -> CAN ID: буфер 9 -> ID 107 (частоты поля), буфер 11 -> ID 109
  (gain/flags). Ранее буфер 9 не инициализировался вовсе, а буфер 11 ошибочно нёс ID 107.
- Буферы 31/32 (>= TX_BUFF_SIZE=16, молча дропались) перемаплены в индексы 14/15.

MCU (INVERTOR_CCS, F28P550SJ9, M_CAN):
- SysConfig: битовый тайминг 1 Мбит/с (арбитраж) + 2.5 Мбит/с (данные, BRS); TX-секция
  Message RAM переведена на 64-байтные элементы (RX оставлен 8-байтным).
- Все TX-буферы телеметрии — CAN FD + BRS.
- Консолидированный медленный кадр: ID 140, DLC=15 (64 байта), буфер 6 = 8 блоков x 4 слова
  (100,101,102,106,107,109,118,116). send_REF_kadr() собирает локальный tele[32] и шлёт
  ОДНИМ вызовом Send_mbox_FD(6, tele, 32); логика вычислений и счётчиков сохранена.
- Send_mbox_FD переписана под C28x-корректную упаковку (uint16_t*, байт = 16 бит); прежняя
  версия с uint8_t* / (uint32_t*)-cast была неработоспособна на C28x.
- Приоритет M_CAN по наименьшему Message ID: ACK(1) > fast(103/104/110) > ошибки(131/132)
  > медленный консолидированный(140) — большой 64-байтный кадр не задерживает важное.

PC / WinForms (ICDIBasic):
- CANA.cs: приём через ReadFD; ранняя ветка `if (ID==140) Parse140(...)` минуя 8-байтный
  ToClassic; добавлен ретрай подключения PCAN (300 мс).
- Kadr60.cs: Parse140 разбивает 64 байта на 8 блоков по 4 слова и вызывает СУЩЕСТВУЮЩИЕ
  ProcessFrame100/101/102/106/107/109/118/116 без изменений их тел (порядок байт little-endian).
- fdBitrate PCAN: 1 Мбит/с арбитраж / 2.5 Мбит/с данные (data_tseg1=23, data_tseg2=8).

Риски / ограничения:
- 5 Мбит/с недостижим на текущем железе (трансивер + проводка). Для 5 Мбит нужен быстрый
  CAN FD SIC трансивер, кабель < 1 м, строго 2x120 Ом, короткие стабы.
- Быстрый кадр (103/104/110) — заготовка: уходит только после инициализации EPWM (шлётся из
  MainISR); на момент версии EPWM ещё не инициализирован.
- Элементы формы, чьи данные лежат в циклирующих блоках (101/102/106/116), снимают жёлтый фон
  через несколько 50-мс циклов (по мере смены счётчика группы) — штатно, как и при 8-байтных.

Примечание:
- Статус проверки на стенде: подтверждено на железе. Parse140 срабатывает; заголовок буфера 6
  прочитан отладчиком (ID=140, DLC=15, FDF=1, BRS=1); ECR=0 (TEC=0) под потоком 64-байтной
  телеметрии FD+BRS.
