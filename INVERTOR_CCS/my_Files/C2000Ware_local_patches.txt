How these guards actually work (read this first - the three patches use THREE DIFFERENT
mechanisms, which is the usual source of confusion)

Patch 2 is the only one that is "first include wins".
  #ifndef means "define only if this name is still free", so exactly one definition survives per
  translation unit - the one that got there first.
  - TI ALREADY guards the bitfield side: f28p55x_device.h line ~160 has #ifndef SUCCESS / #ifndef FAIL.
    The driverlib side (stw_types.h) was the only bare one, which is why only it needed patching.
  - Actual include order in this project is driverlib FIRST, not bitfield: nearly every .c starts with
    board.h, and board.h line 52 is #include "driverlib.h". In main.c driverlib.h is line 16 while
    f28p55x_device.h is line 34. So in practice driverlib wins and TI's bitfield guard quietly yields.
  - The #48-D warning came from the minority of translation units with the reverse order (a .c that
    pulls e.g. myADC.h -> f28p55x_device.h before driverlib): there bitfield defined SUCCESS first and
    unguarded driverlib redefined it.
  - So the POINT OF THE GUARD IS NOT to force an include order. It is to make the order irrelevant.
    Both sides guarded => whoever comes first wins and nobody warns. Do NOT reorder includes to "fix"
    this; that is not what the patch is for.
  - Side effect worth knowing: the TYPE of SUCCESS now depends on include order in each .c file -
    true (_Bool) in some, ((uint32_t)1U) in others. The VALUES agree (1 and 0), so comparisons are
    safe; sizeof or type deduction would not be.

Patch 1 is NOT about "who defined it first".
  Its outer #ifndef tests _DUAL_HEADERS - a BUILD FLAG, not the macro IDLE. This project always
  passes --define=_DUAL_HEADERS, so the #else branch is taken and IDLE is never defined at all,
  regardless of include order. That is what frees the name IDLE for bitfield fields/prototypes.
  The inner #ifndef IDLE only lives in the non-_DUAL_HEADERS branch, i.e. never in our build.

Patch 3 is not about macros at all.
  It guards six extern declarations. The conflict is a TYPE mismatch - Uint16 in the bitfield header
  vs uint16_t in the SysConfig-generated device.h - and the condition is again a build flag (_FLASH),
  not "who came first". The guard simply removes one of the two declarations in FLASH builds.

Effect (important, it is not a plain include guard): with _DUAL_HEADERS defined - which this project
      always does - the #else branch is taken and the macro IDLE is NOT defined at all; IDLE_ASM
      takes its place. That is the whole point: it frees the name IDLE for bitfield fields and
      prototypes. Consequence: the asm IDLE instruction must be written as IDLE_ASM. Not an issue
      here - the only occurrence is bitfield_source/f28p55x_sysctrl.c:674, its own IDLE() function
      using a direct asm(" IDLE"), and that file is excluded from the build in both configurations.
Reason: Macro IDLE conflicts with bitfield field/prototype names (f28p55x_lin.h, f28p55x_globalprototypes.h).
Applied form:
#ifndef _DUAL_HEADERS
#ifndef IDLE
#define IDLE   __asm(" IDLE")
#endif
#else
#define IDLE_ASM __asm(" IDLE");
#endif

Patch 4 (local clangd config - editor only, does not affect the build)
File: %LOCALAPPDATA%\clangd\config.yaml  (C:\Users\<user>\AppData\Local\clangd\config.yaml)
Reason: C2000Ware headers gate their whole body on the cl2000 built-in macro __TMS320C28XX__
        (e.g. driverlib\f28p55x\driverlib\mcan.h line 53). That macro is built into the compiler,
        so it never appears in CPU1_FLASH\.clangd\compile_commands.json - clangd does not see it
        and greys out the entire header.
Why here and not in the project: INVERTOR_CCS\.clangd is auto-generated by CCS (it says so in its
        own header), is in .gitignore, and gets overwritten on every index regeneration - a fix
        placed there is lost. It also only applies to files inside the project tree, while the
        affected headers live under C:\ti\C2000Ware_*. The user-level config is the only place CCS
        does not touch that also covers SDK paths.

    - .*[/\\]ti[/\\]ccs.*

  Add:
    - -D__TMS320C28XX__=1

  it eats LS the CLA wants.
