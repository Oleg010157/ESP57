Patch 4 (local clangd config - editor only, does not affect the build)
File: %LOCALAPPDATA%\clangd\config.yaml  (C:\Users\<user>\AppData\Local\clangd\config.yaml)
Reason: C2000Ware headers gate their whole body on the cl2000 built-in macro __TMS320C28XX__
        (e.g. driverlib\f28p55x\driverlib\mcan.h line 53). That macro is built into the compiler,
        so it never appears in CPU1_FLASH\.clangd\compile_commands.json - clangd does not see it
        and greys out the entire header.
Why here and not in the project: INVERTOR_CCS\.clangd is auto-generated by CCS (it says so in its
        own header), is in .gitignore, and gets overwritten on every index regeneration - a fix
        placed there is lost. It also only applies to files inside the project tree, while the
        affected headers live under C:\ti\C2000Ware_*. The user-level config is the only place CCS
        does not touch that also covers SDK paths.
Applied form:
If:
  PathMatch:
    - .*[Cc]2000[Ww]are.*
    - .*[/\\][Ww]ork[/\\]K55[/\\].*
    - .*[/\\]ti[/\\]ccs.*
CompileFlags:
  Add:
    - -D__TMS320C28XX__=1
Verification:
  C:\ti\ccs2100\ccs\theia\resources\clangd\clangd.exe --check=<path to mcan.h>
  - log must contain "Loading config file at ...AppData\Local\clangd\config.yaml"
  - the printed cc1 args must contain "-D __TMS320C28XX__=1"
  - parsing must now reach the lines inside the #ifdef (before the fix it skipped straight past it)
Known residue (not fixed, editor-only, no effect on the build):
  With the block active, clangd reports a couple of errors inside mcan.h that the real cl2000 build
  does not have:
  - inc\hw_types_mcan.h uses uint32_t without including <stdint.h> (the header is not self-contained;
    in a real TU stdint comes in earlier via device.h).
  - cpu.h uses cl2000-only extensions __cregister / __enable_interrupts, which clang does not know
    at all.
  This is why the CCS-generated project .clangd carries "Diagnostics: Suppress: '*'". Left
  unsuppressed for SDK headers per user's choice.
No CCS setting can turn the regeneration off (checked in CCS 21.0.0, 2026-08-09):
  The writer is com.ti.ccs.server.core.ClangdCompilationDatabaseGenerator inside
  ccs\eclipse\plugins\com.ti.ccs.server_21.0.0.*.jar, registered in plugin.xml as a plain listener
  on extension point com.ti.ccs.project.projectStateListeners - no enablement condition. That
  plugin contributes no preference or property pages at all, and the file body is a hardcoded
  constant (CLANGD_CONFIGURATION_FILENAME / CLANGD_CONFIGURATION_CONTENT) with no hook to append
  flags. The Theia-side ccs-project / ccs-ai extensions contribute no clangd settings either, and
  clangd itself has no --extra-arg, so clangd.arguments cannot inject a define. Also note
  compile_commands.json is rewritten on every build, so hand-patching it is pointless.
Rejected alternative - do NOT retry (tested 2026-08-09):
  Putting --define=__TMS320C28XX__=1 into the project compiler options would be git-portable
  (.cproject is tracked, and CCS launches clangd with --compile-commands-dir pointing at
  CPU1_FLASH\.clangd, so the define would reach SDK headers too). But CCS applies compiler options
  to EVERY source file, including .cla files, which are built by the CLA compiler where
  __TMS320C28XX__ must stay undefined. Result: CLA\Task1.cla and CLA\Task7.cla each failed with
  43 errors - "#838: unrecognized cregister name 'IFR'/'IER'" in f28p55x_device.h and a long list
  of "identifier CLA_O_* is undefined" in cla.h, because the C28-only parts of the headers got
  exposed to the CLA build. Reverted via git checkout of .cproject; CLA builds cleanly again.
  Standalone cl2000 does NOT warn about redefining the built-in macro, so a quick syntax test on a
  plain .c file looks fine and hides this - the failure only shows on .cla files.

CPU1_FLASH build configuration notes (2026-07-26)
CPU1_FLASH was never fully brought up to parity with CPU1_RAM. To make it build:
- SysConfig tool flags for CPU1_FLASH used unresolved build variables
  (${COM_TI_C2000WARE_SYSCONFIG_MANIFEST} / ${SYSCONFIG_TOOL_SYSCONFIG_MANIFEST}) that silently
  evaluated to empty, so sysconfig_cli.bat fell back to the .syscfg file's own embedded @cliArgs
  product version ("C2000WARE@26.01.00.00"), which CCS's product registry does not recognize
  (it knows the SDK as "26.1.0.00"). Fixed by appending explicit flags via setToolFlags:
  -s "C:/ti/C2000Ware_26_01_00_00/.metadata/sdk.json" -d "F28P55x" -p "100PZ" -r "F28P55x_100PZ"
- Compiler flags for CPU1_FLASH were missing --define=_DUAL_HEADERS and several include paths
  that CPU1_RAM has (KSP, CLA, my_Files, C2000Ware_COMMON, CLAmath, FlashAPI, PROJECT_LOC/../bin,
  C2000WARE_DLIB_ROOT/inc), plus --idiv_support=idiv0 --vcu_support=vcu2 --fp_mode=relaxed
  --cla_signed_compare_workaround=on. Added via setToolFlags to mirror CPU1_RAM.
- Per-file build exclusions were missing for CPU1_FLASH (present in CPU1_RAM for the same reasons
  as Patch 1/3 above - these files conflict with globalprototypes.h in dual-header mode):
  bitfield_source/f28p55x_sysctrl.c, bitfield_source/f28p55x_gpio.c,

  Build... -> check the configuration.

uninitialized/zero-init section gets an auto-synthesized ".cinit.X.load" companion section for
the load image, and THAT auto-generated companion (not the run placement) is what triggers the
warning. Confirmed harmless via the .map file. Left unsuppressed per user's choice; could be
silenced with --diag_suppress=10247 on the CPU1_FLASH linker if ever wanted.

Change log
- 2026-08-10: CRITICAL - found that --idiv_support=idiv0 (the default IDE setting, "enhanced integer
  division instruction extension") produces WRONG results for int32_t/int16_t division on this
  device+toolchain combo (ti-cgt-c2000_25.11.1.LTS, F28P55x, CPU1_FLASH config, -Ooff). Minimal
  repro: `int32_t dbg_mul=974848; int16_t dbg_slope=25987; dbg_mul/dbg_slope` compiles to 0 on
  target with idiv0, but the CCS debugger's own expression evaluator computes the same expression
  (same live memory) as 37 - proving it's a real code-gen/silicon issue, not a logic error. A
  float-cast division `(int32_t)((float)dbg_mul/(float)dbg_slope)` gave the correct 37 even with
  idiv0 still enabled, confirming FPU division is unaffected - only the idiv0 integer path is
  broken. This was discovered while debugging ADC_getTemperatureC() (adc.h) returning 0 for
  core_temp instead of a plausible ~36 degC - that function's return statement does exactly this
  int32/int16 division pattern.
  FIX APPLIED: set CPU1_FLASH compiler flag --idiv_support=none via setToolFlags (appends after the
  IDE's own --idiv_support=idiv0; CCS's per-option build-definition tracking makes the later value
  win, confirmed in invertor_build.log - only "--idiv_support=none" appears in the actual cl2000
  invocation). Verified: core_temp now reads 36 on live hardware after this change, matching hand
  calculation. NOT YET APPLIED to CPU1_RAM config - if that config is ever used for real hardware
  testing (not just RAM debug), apply the same flag there.
  IMPORTANT - project-wide risk: idiv0 was the project's setting from the start, so any other
  int32/int16 (or int32/int32 via a 16-bit-typed operand) division elsewhere in the existing
  codebase may have been silently wrong before this fix, on F28P55x specifically. Worth an audit if
  strange numeric behavior shows up elsewhere (protection thresholds, calibration math, etc.).
  TODO: consider reporting to TI as a compiler/toolchain bug (ti-cgt-c2000_25.11.1.LTS,
  --idiv_support=idiv0, F28P55x) since a wrong division result is a serious silent-corruption class
  of bug.
