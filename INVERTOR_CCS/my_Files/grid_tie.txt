0. ГЛАВНАЯ МЫСЛЬ
--------------------------------------------------------------------------------

Синхронизация - необходимое условие, но не достаточное. Пока мост работает
источником НАПРЯЖЕНИЯ (sine_invertor1/2 кладут в CMPA заранее посчитанную
синусоиду), подключение к сети даёт неуправляемый ток: два источника напряжения
рядом обмениваются током, равным их разности, делённой на импеданс.

Посчитаем, насколько это плохо. Индуктивность рассеяния трансформатора,
приведённая к вторичке, порядка 8 мГн, то есть 2.5 Ом на 50 Гц. Ошибка
амплитуды в 1 % - это 3 В, то есть 1.2 А. Ошибка фазы в 1 градус - это 5.4 В,
то есть 2.2 А. И никакой уставки мощности при этом не существует: мы не задаём
ток, мы только смотрим, какой получился.

Поэтому мост переводится в режим источника ТОКА. Фазу берём у уже работающего
PLL, а замкнутый контур держит мгновенный ток i = Iзад*sin(theta). Тогда
мощность - это уставка, а ток ограничен по определению.

    ЧТО БЫЛО: задаём напряжение, ток получается сам
    ЧТО СТАЛО: задаём ток, напряжение мост подбирает сам


0.1 ТОПОЛОГИЯ И КТО ГДЕ ЖИВЁТ
--------------------------------------------------------------------------------

    АКБ 24..60 В -> H-мост (EPWM1 = плечо A, EPWM2 = плечо B)
                 -> повышающий трансформатор 50 Гц, 3 кВт
                 -> сеть 220 В

    grid_tie_step()        каждое прерывание ADCB, 100 раз за период сети.
                           Контур тока, модулятор, быстрые защиты, модель.
                           Вызывается из INT_myADCB_1_ISR (1ph_Sin.c).
                           Почему ADCB, а не EPWM1 - раздел 2.

    grid_tie_onGridZero()  раз за период сети, из INT_U220_zero_ECAP_ISR.
                           Автомат, нарастание уставки, контур подавления DC.

    grid_tie_background()  из while(1) в main.c. Закрытие IGBT и запись
                           аварии в журнал - то, чему не место в прерывании.

Всё выключается одним флагом:

    gridMode = 0   АИН: своя частота, своя уставка напряжения (по умолчанию)
    gridMode = 1   сетевой режим

При gridMode = 0 grid_tie_step() не вызывается вообще - токового контура в
острове нет. "Разомкнутым контуром" остров работал до 25.09.2026; теперь
напряжение там держит свой замкнутый контур, см. раздел 11. От этого файла в
острове работают три вещи: grid_tie_measure() (измерения и два разрешения),
grid_tie_apply_uref() (амплитуда, каждый такт) и grid_tie_background()
(закрытие ключей и журнал).


1. КОНТУР ТОКА
--------------------------------------------------------------------------------
   Где: grid_tie_step(), grid_tie.c

Вся математика ведётся на стороне сети (вторичка), в вольтах и амперах.
Коэффициент трансформации входит ровно один раз, в самой последней строке.

    theta = sineB.angle + sineB.offset  // угол сети, от PLL по нулю U220 (ECAP1)
    iref  = gt.Iset * sinf(theta)       // Iset  - амплитуда тока в сеть, А. Это уже
                                        //         результат нарастания: IsetRef -
                                        //         чего хотим, Iset - что отдаём сейчас
    err   = iref - gt.Ib_amp            // Ib_amp - измеренный ток вторички, А
    u_sec = gt.uGrid + PR(err)          // uGrid - мгновенное напряжение сети, В.
                                        //         Не из PPB, см. 1.0. Это прямая
                                        //         связь, см. 1.1
                                        // PR()  - резонансный регулятор, см. 1.2
    m     = u_sec / (gt.n * gt.Udc) + mDC
                                        // n     - коэффициент трансформации
                                        //         Uвтор/Uперв, на стенде 7
                                        // Udc   - мгновенное напряжение АКБ, В.
                                        //         n*Udc - вся амплитуда, какую мост
                                        //         может выдать на стороне сети
                                        // mDC   - поправка контура подавления
                                        //         постоянной составляющей, см. 3.1

1.0 ОТКУДА БЕРЁТСЯ uGrid - ГРАБЛИ, НА КОТОРЫЕ УЖЕ НАСТУПИЛИ

Напряжение сети НЕ берётся из ADCPPB1RESULT, хотя это выглядит очевидным
и именно так делает Task1.cla.

Причина: в syscfg у PPB1 стоит ppb1ReferenceOffset = 2048, но в живой
системе ADCPPB1OFFREF содержит КАЛИБРОВОЧНЫЙ ноль канала - на стенде это
offsets_default.Udc = 110. То есть "знаковый" результат PPB несёт постоянное
смещение почти в 2000 кодов.

Симптом был такой: индекс модуляции полпериода стоял в упоре (satLast = 47
из 100), хотя расчётный пик m = 272/(7*48) = 0.81, далеко от потолка 0.95.

Поэтому берётся сырой отсчёт минус измеренный ноль:

    gt.uGridKod = u220_kod - gt.u220Zero
    gt.u220Zero = (u220hi_kod + u220low_kod) / 2      // раз за период сети

Ноль - середина вилки огибающей из myADC.c. Вилка обхватывает реальный
сигнал сверху и снизу, значит её середина и есть ноль, причём измеренный,
а не предположенный. На стенде получается 2063..2070.

Мораль на будущее: у токов ADCPPB*OFFREF - это правильный ноль, его туда
кладёт Adc_Calibrate(). У U220 - нет, там калибровка канала осталась от
прежнего назначения этого входа (Udc).


1.1 ПРЯМАЯ СВЯЗЬ - ГЛАВНАЯ ХИТРОСТЬ

Обрати внимание на слагаемое gt.uGrid. Это измеренное мгновенное напряжение
сети, и оно снимает с регулятора всю основную синусоиду. Регулятору остаётся
отработать только падение на индуктивности рассеяния, а это единицы вольт при
сотнях вольт самой сети.

Без прямой связи PR пришлось бы синтезировать все 311 В пика самостоятельно,
с большим усилением и на грани устойчивости. С ней коэффициенты получаются
скромными, а запас устойчивости хорошим.

1.2 ПОЧЕМУ PR, А НЕ PI

PI даёт нулевую установившуюся ошибку только по постоянной величине. Наш
сигнал - синусоида 50 Гц, и PI на ней всегда отстаёт и по амплитуде, и по фазе.

PR (proportional-resonant) имеет бесконечное усиление на одной частоте -
резонансной. Ставим резонанс на 50 Гц, и ошибка на этой частоте уходит в ноль
без всяких преобразований координат.

Реализация - пара связанных интеграторов, без единого вызова sinf/cosf:

    x1 += step*x2 + KiTs*e - leak*x1
    x2 -= step*x1
    out = Kp*e + x1

Это дискретный генератор, вращающийся с шагом step за такт. И вот что здесь
красиво: step берётся прямо из sineB.step. А sineB.step вычисляется в ECAP-
прерывании из ИЗМЕРЕННОГО периода сети. То есть резонанс автоматически сидит
точно на частоте сети и едет за ней, если та поплывёт. Бесплатно, потому что
ШИМ жёстко синхронна с сетью: ровно 100 периодов ШИМ на период сети.

leak (0.002) делает регулятор неидеальным - усиление на резонансе конечно.
Без него пара интеграторов была бы незатухающим генератором, и любая
случайно накопленная энергия осталась бы в нём навсегда.

1.3 АНТИ-ВИНДАП ОТКАТОМ

При упоре по m состояние резонатора откатывается на значения до обновления:

    if (упор) { x1 = x1old; x2 = x2old; satCount++; }

Это условное интегрирование в самой простой форме. Регулятор в упоре
не наматывает, и после выхода из упора не приходится ждать, пока он
размотается обратно.

ЧТО КРУТИТЬ:
    gt.pr.Kp = 2*PI*f_bw*L,   f_bw ~ 300 Гц - потолок при Ts = 200 мкс
    gt.pr.Ki = Kp*w_r,        w_r ~ 2*PI*20 - ноль ошибки за ~50 мс
    gt.pr.leak                больше = устойчивее, но ошибка не до нуля

Откуда взять L: закоротить вторичку, подать на первичку небольшое напряжение,
померить ток. Получится Z короткого замыкания, из него L. Отдельный дроссель
при трансформаторе на выходе не нужен - рассеяние и есть фильтр.


2. ЗАДЕРЖКА КОНТУРА - ПОЧЕМУ ТАКТ ВИСИТ НА АЦП, А НЕ НА ШИМ
--------------------------------------------------------------------------------
   Переделано 19.08.2026.

2.1 КАК БЫЛО И ПОЧЕМУ ЭТО БЫЛО ПЛОХО

Обработчик сидел на прерывании EPWM1 по TBCTR = PRD. Ровно этим же событием
запускается ADCB SOCA. Два события в один момент - значит в начале ISR в
регистрах результата лежал отсчёт ПРОШЛОГО периода: преобразование текущего
только начиналось. Плюс полтакта на загрузку CMPA из теневого регистра по
TBCTR = 0.

Итого от момента выборки до момента, когда новый CMPA реально начинает
действовать, проходило 1.5 такта, то есть 300 мкс. На 300 Гц это 32 градуса
фазового запаздывания - оно и упирало полосу тока в эти самые 300 Гц.

Отставал не только ток. u220_kod писало тогда отдельное прерывание ADCA INT1,
и срабатывало оно уже ПОСЛЕ прежнего обработчика - значит прямая связь gt.uGrid
(раздел 1.1), несущая всю сетевую синусоиду, отставала на тот же такт.
В установившемся режиме PR это дожимал бесконечным усилением на 50 Гц, так
что в осциллограммах это не бросалось в глаза - но состояние резонатора
тратилось впустую, а на переходных процессах ошибка вылезала целиком.

2.2 КАК СТАЛО

Такт управления переехал на прерывание ADCB INT1 по EOC1 - концу
преобразования Ib. Запуск АЦП не изменился, по-прежнему EPWM1 SOCA по
TBCTR = PRD. Изменился только момент, когда просыпается код: примерно через
1.2 мкс после TBCTR = PRD, когда Ia и Ib уже оцифрованы.

    было:  выборка ---- 1 такт ---- ISR --- 0.5 такта --- CMPA действует
    стало:                     выборка + 1.2 мкс = ISR --- 0.5 такта --- CMPA

Задержка стала 0.5 такта, 100 мкс. На 300 Гц это 10.8 градуса вместо 32 -
с контура снят 21 градус фазового запаздывания даром, без единого лишнего
такта вычислений.

Ниже 0.5 такта не уйти, и не надо: остаток - это теневая загрузка CMPA по
TBCTR = 0, на ней держится симметрия ШИМ.

Порядок с вилкой U220 тогда получился правильным сам собой, через приоритеты
PIE: ADCA1 = INT1.1 стоит выше ADCB1 = INT1.2. С 23.09.2026 полагаться на это
не нужно вовсе - прерывание ADCA снято, а его код стал функцией u220_sample()
в начале нашего же такта. Порядок теперь виден строками, а не выводится из
таблицы приоритетов.

2.3 ЧТО ИЗ ЭТОГО СЛЕДУЕТ И ЧТО ПРОВЕРИТЬ

Kp пока НЕ трогали. Потолок f_bw вырос, но насколько - вопрос к железу, а не
к арифметике: Ts = 200 мкс и шаг резонатора остались прежними. Поднимать Kp
только по стенду, отслеживая свист.

Новый режим отказа: раньше контур крутился, пока жив таймер EPWM1. Теперь -
пока идёт SOCA. Если АЦП по какой-то причине перестанет запускаться, модулятор
замрёт с последним CMPA, а не встанет в ноль. Отсюда и ручной сброс флага
ADCINT1 в конце обработчика, хотя при continuous mode он не обязателен: пусть
по флагу видно, живой такт или зависший.

Прерывание EPWM1 погашено в main.c сразу после Board_init(). Обработчик
INT_myEPWM1_ISR оставлен пустой заглушкой только потому, что SysConfig пока
регистрирует вектор. Снимешь галку "Enable Interrupt" у myEPWM1 - удаляй
и заглушку, и две строки в main.c.

Ts = 200 мкс берётся из того, что sineB.resolution = 100 точек на период сети.
Подняв resolution до 200, получишь 10 кГц и вдвое меньшую задержку - но сначала
проверь по sine_Time, что прерывание укладывается.


3. ТРАНСФОРМАТОР: ЧЕМ ОН ОПАСЕН
--------------------------------------------------------------------------------

3.1 ПОСТОЯННАЯ СОСТАВЛЯЮЩАЯ
   Расширено 19.08.2026.

Это здесь главный враг, важнее перегрузки по току.

С дросселем DC-смещение даёт просто постоянный ток - неприятно, но не
смертельно. С трансформатором оно НАМАГНИЧИВАЕТ СЕРДЕЧНИК. Поток - интеграл
напряжения, и постоянная составляющая напряжения интегрируется без границ.
За несколько периодов сердечник уходит в насыщение, индуктивность падает
почти до нуля, и ток намагничивания взлетает на порядок. Ключи гибнут раньше,
чем это заметит любая медленная защита.

Ниже - почему счёт идёт именно на периоды, почему контур тока не справится
с этим сам, и что в контуре подавления пока не проверено.


3.1.1 БЮДЖЕТ ПО ПОТОКУ - ОТКУДА "НЕСКОЛЬКО ПЕРИОДОВ"

У сердечника есть конечный запас вольт-секунд, и постоянка выедает его
линейно во времени. Амплитуда потокосцепления первички на рабочей синусоиде:

    lambda_pk = U_pk / w = (311/7) / 314 = 44.4 / 314 = 0.141 В*с

Это именно АМПЛИТУДА, а не интеграл за полволны. Интеграл синуса даёт косинус,
поток качается от -lambda_pk до +lambda_pk, полный размах вдвое больше -
0.28 В*с. С B_sat сравнивают амплитуду, поэтому в расчёте запаса нужна она.

Косинус против синуса означает ещё и вот что: поток максимален в НУЛЕ
напряжения и равен нулю в МАКСИМУМЕ напряжения. Это та же формула, что
объясняет правило пуска из 3.4.

Теперь про запас. B - индукция в сердечнике, тесла. С потокосцеплением она
связана жёстко и линейно:

    lambda = N * Ф = N * B * S     N - витки первички, S - сечение железа

N и S - константы конкретного трансформатора, поэтому любое ОТНОШЕНИЕ потоков
есть ровно то же отношение индукций. Считать можно в чём удобнее, а удобнее в
вольт-секундах: их я меряю прямо через напряжение и время, не зная ни N, ни S.

B_sat - индукция насыщения, уровень, выше которого железо перестаёт быть
железом: проницаемость падает почти до воздушной, индуктивность обваливается,
ток намагничивания перестаёт быть маленьким. Для трансформаторной стали
на 50 Гц это порядка 1.8..2.0 Тл.

Проектировщик не сажает рабочую точку в само насыщение - нужен запас на
повышенное сетевое, нагрев, гармоники. Типично берут

    B_max ~ 0.8 * B_sat            то есть 1.4..1.6 Тл

Отсюда и четверть. Свободного места остаётся 0.2*B_sat, но относить его надо
к РАБОЧЕЙ АМПЛИТУДЕ, а не к B_sat - потому что бюджет тратится в тех же
единицах, в которых меряется lambda_pk:

    (B_sat - B_max) / B_max = 0.2*B_sat / 0.8*B_sat = 0.25

    запас = 0.25 * lambda_pk = 0.25 * 0.141 = 0.035 В*с

"Двадцать процентов" и "четверть" здесь одно и то же число, просто отнесённое
к разному: первое к B_sat, второе к рабочей точке.

ПОЧЕМУ ЭТО СКЛАДЫВАЕТСЯ. Постоянка не увеличивает размах колебания - она
сдвигает всю синусоиду потока вверх. Поток качается на +-lambda_pk вокруг
смещения lambda_dc, значит потолка достигает ОДИН пик из двух:

    lambda_dc + lambda_pk > lambda_sat   <=>   lambda_dc > 0.035 В*с

Насыщение получается ОДНОСТОРОННИМ, и это его опознавательный знак: всплески
тока намагничивания идут через период, только в одной полуволне. Увидишь такое
на осциллограмме Ia_amp - это постоянка, а не перегрузка.

0.8 - ПРЕДПОЛОЖЕНИЕ, А НЕ ИЗМЕРЕНИЕ. Таблица ниже линейно на нём висит:

    B_max/B_sat   запас от амплитуды   все времена в таблице
    ------------------------------------------------------------
    0.7           0.43                 x1.7
    0.8           0.25                 как в таблице
    0.9           0.11                 x0.44

Уточняется двумя способами. Прямо: B_max = lambda_pk/(N*S) по реальным виткам
и сечению. Обратная прикидка при B_max = 1.4 Тл и S = 20 см2 даёт
N = 0.141/(1.4*0.002) = 50 витков первички - для 48 В и 3 кВт похоже на правду,
то есть порядок сходится. Опытом: на холостом ходу поднимать напряжение и
смотреть ток намагничивания. Пока растёт линейно - запас есть; где ломается
вверх - там колено, и отношение напряжений даёт B_max/B_sat.

Дальше просто деление - сколько живёт сердечник при постоянке U_dc на первичке:

    U_dc на первичке   до насыщения   периодов   что это такое
    ------------------------------------------------------------------------
    1.8 В              20 мс          1
    0.96 В             37 мс          1.8       mDC на потолке, см. 3.1.5
    0.48 В             73 мс          3.7       полная ошибка dead-time (9.3)
    0.048 В            0.73 с         37        разброс плеч, 10 % от неё

Даже исправленный метод 2 с его остаточными 10 % без контура подавления кладёт
сердечник меньше чем за секунду. Вот что стоит за словами "за несколько
периодов".


3.1.2 ОТКУДА БЕРЁТСЯ DC

    - асимметрия мёртвого времени: 150 тактов = 2 мкс при периоде ШИМ 200 мкс,
      то есть 1 %. Полная вольт-секундная ошибка 0.48 В, см. 9.3
    - смещение нуля датчика ВТОРИЧКИ. Контур тока на постоянке - это голый Kp
      (см. 3.1.3), поэтому ошибка всего 0.1 А даёт 15*0.1 = 1.5 В на вторичке,
      то есть 0.21 В на первичке, то есть mDC = 0.0045. Четверть всего бюджета
      mDCmax - из-за одного смещения датчика
    - смещение нуля датчика ПЕРВИЧКИ. Контур зануляет ИЗМЕРЕННОЕ среднее,
      значит реальное среднее уедет ровно на смещение датчика. Точность
      подавления не может быть лучше точности нуля Ia_amp, см. 7.2
    - смещение компаратора


3.1.3 ПОЧЕМУ КОНТУР ТОКА НЕ СПРАВИТСЯ САМ

Казалось бы, замкнутый контур тока уже есть - пусть он постоянку и давит.
Не сможет, и это видно прямо из уравнений резонатора:

    x1 += step*x2 + KiTs*e - leak*x1
    x2 -= step*x1
    out = Kp*e + x1

Подставим постоянную ошибку e и поищем равновесие. Чтобы x2 не менялась,
нужно step*x1 = 0, то есть x1 = 0. Тогда из первой строки x2 = -KiTs*e/step,
а на выход остаётся только Kp*e.

Вся бесконечная добротность PR сидит ровно на 50 Гц и на нуле герц не даёт
НИЧЕГО. На постоянке это обычный П-регулятор с усилением 15. Поэтому контур
подавления DC - отдельный, и он не украшение, а условие выживания.

Побочно: x2 в равновесии паркуется на ненулевом значении и, в отличие от x1,
клампа не имеет вообще. При нынешних числах это мелочь (x2 = -6*e), но знать
стоит.


3.1.4 САМ КОНТУР: ПЕРВИЧКА, ЗНАК, ОКНО
   Переписан 24.09.2026: контур целиком уехал в CLA, окно стало одно.

    iPri_av = среднее тока первички за окно
    mDC    -= kDC * iPri_av          ограничено |mDC| < mDCmax

ГДЕ ОН ЖИВЁТ. Целиком в Cla1Task1 - и усреднение, и интегратор, и ограничение,
и сброс. CPU не считает из него НИЧЕГО: он только применяет готовый mDC к
ключам и сообщает задаче два слова - dcAllow (можно ли сейчас править) и
dcResetReq (пора начать сначала).

Это то же правило, по которому туда ушли действующие значения и мощности:
CPU МЕРЯЕТ, CLA СЧИТАЕТ. Арифметика раз за период - ровно та работа, ради
которой CLA и ставят, а окно у неё уже было заведено под RMS.

До того интегратор жил на CPU двумя обёртками, своей на каждый режим моста,
и держал своё представление об окне. Разбор того, почему это ушло, - в конце
раздела.

ПОЧЕМУ ПЕРВИЧКА. Ток намагничивания течёт по контуру намагничивания, то есть
только в первичке, и во вторичку не трансформируется в принципе. Мерить
постоянку по току вторички - значит мерить всё, кроме той единственной
величины, которая губит сердечник.

ПОЧЕМУ МЕДЛЕННО. Задача - убрать систематическое смещение, а не гоняться за
динамикой. Вторая причина, менее приятная, в 3.1.6.

ЗНАК. m = uSec/(n*Udc) + mDC, значит положительный mDC даёт положительное U_AB
и положительный постоянный ток из моста. mDC -= kDC*iPri_av - отрицательная
обратная связь. НО только при gt.iSign = +1.

При неверном iSign контур становится ПОЛОЖИТЕЛЬНОЙ обратной связью и за
считанные периоды уезжает в потолок mDCmax - то есть ровно в тот почти вольт,
который по таблице 3.1.1 насыщает сердечник за два периода. Защита превращается
в самый быстрый способ убить трансформатор. Контур тока при неверном знаке
разойдётся раньше и всё уронит по gt_overIsec, так что скорее всего до этого не
дойдёт - но полярность датчиков (7.3) проверяется ДО первого включения,
а не по факту.

ОКНО УСРЕДНЕНИЯ. Оно обязано быть ЦЕЛЫМ ЧИСЛОМ ПЕРИОДОВ выходного напряжения:
только в таком окне основная гармоника даёт строгий ноль и не просачивается
в оценку постоянки.

Окно одно на оба режима - rmsWindow тактов, то же самое, которым CLA считает
действующие значения. rmsWindow есть копия sineB.resolution, её кладёт
change_sine(), и через неё проходит ЛЮБОЕ изменение resolution (команды CAN
621/62x и инициализация), другого пути нет.

Целым числом периодов оно получается в обоих режимах, но по разным причинам:

    в острове     угол синуса двигается на 2*PI/resolution каждый такт,
                  значит resolution тактов - ровно период, по построению
    в сети        период EPWM1 подстроен PLL так, что на период сети
                  приходится ровно resolution отсчётов

ПОЧЕМУ НЕ ОКНО ПО НУЛЮ СЕТИ, как было в сетевом режиме до 24.09.2026. Оно
казалось надёжнее - границу ставит сама сеть, - но платой было дрожание
границы относительно сетки тактов: в окно попадало 99 или 101 отсчёт, и
лишний отсчёт амплитудой до 35 А давал до 0.35 А ложной "постоянки". Делением
на фактический счётчик это не лечится: сумма 101 отсчёта синуса не ноль, чем
ни дели.

Окно по тактам от этого свободно: сумма основной гармоники по РАВНООТСТОЯЩИМ
resolution точкам за период равна нулю ТОЧНО, по симметрии. То есть в
установившемся режиме новое окно строго чище прежнего.

ЦЕНА. Равенство "resolution тактов = период сети" держит PLL, и на самом
захвате оно нарушено. Ошибка там того же порядка, что и прежнее дрожание
99/101: при расхождении частоты на 1 % в оценку просачивается около 0.35 А.
То есть в худшем случае разменяли шило на мыло, а в установившемся выиграли.
Неприятно это тем, что захват PLL приходится как раз на GT_SYNC - самое
опасное для сердечника состояние (3.1.7). ПРОВЕРИТЬ НА ЖЕЛЕЗЕ: смотреть
iPri_av в GT_SYNC до захвата и после, разница и есть эта ошибка.

ЗАПАЗДЫВАНИЕ. Задачу CLA взводит последняя строка такта управления, поэтому
mDC, посчитанный на такте закрытия окна, применяется со следующего: один
такт, 200 мкс. В петле с постоянной времени около секунды это ничто.


3.1.5 mDCmax - ПРЕДЕЛ ПОЛНОМОЧИЙ, А НЕ ПРЕДЕЛ БЕЗОПАСНОСТИ

mDCmax = 0.02 при Udc = 48 В - это 0.96 В постоянки на первичке, то есть по
таблице 3.1.1 меньше двух периодов до насыщения. Потолок выбран из "сколько
нужно для компенсации" (мёртвое время просит 0.01, взят двойной запас),
а НЕ из "сколько сердечник стерпит".

Отсюда смысл упора: это не "контур старается", а "помеха больше всех моих
полномочий". Контур делает что может и проигрывает.

СЧЁТЧИК УПОРА - сделано 24.09.2026, dcSatCnt / dcSatLimit, код gt_dcSat (66).

Считает CLA, разбирает grid_tie_background(). Считаются окна ПОДРЯД, а не
частота событий: одиночный выход на потолок бывает при честной отработке
большого возмущения, серия означает, что помеха сама не кончится. Счётчик
обнуляется и при выходе из упора, и при снятом dcAllow - иначе замороженная
в упоре поправка тикала бы вечно на неработающем мосте.

Порог 50 окон, то есть секунда при 50 Гц. Взят с запасом НАД предсказанным
в 3.1.6 звоном около 1 Гц: на гребне такого колебания поправка законно
простоит в упоре доли секунды, и полусекундный порог кричал бы на собственную
динамику контура. Уточнить, когда звон будет измерен на железе.

РЕАКЦИЯ - ЗАПИСЬ В ЖУРНАЛ СЕССИИ, БЕЗ ОСТАНОВА, и это осознанно.

Ключи бережёт компаратор CMPSS2 по линии TRIP5 (раздел 10.4): аппаратно, за
сотни наносекунд. При обвале индуктивности ток нарастает за микросекунды, и
успевает только он - программная отсечка по gt.ImaxPri работает раз в 200 мкс
и на таком событии формальность. Подменять компаратор этим счётчиком нечем,
да и незачем.

Но есть случай, которого компаратор не видит НАМЕРЕННО. Порог по первичке
ставится как ImaxSec * n * currentLimitMagK, где currentLimitMagK = 1.3
(myADC.c), то есть приведённый ток нагрузки плюс 30 %, и этот запас заведён
как раз затем, чтобы пропускать ток намагничивания. Нормальный ток
намагничивания - проценты от номинала, порог - 130 %. Между ними больше чем
на порядок места, и в этом промежутке целиком помещается сердечник, у
которого поток каждый период стоит не по центру: ток намагничивания вырос в
несколько раз, добавились потери в железе, форма поплыла - и ни одна защита
об этом не скажет. Причём порог привязан к номиналу, а не к текущей нагрузке,
так что на холостом ходу и в GT_SYNC запаса ещё больше.

Вот этот ХРОНИЧЕСКИЙ случай счётчик и называет. Острый случай закрыт
компаратором, и от него же сердечник не страдает: железо от насыщения не
изнашивается, гибнут ключи, а их компаратор и спасает.

Заодно снимается вторая беда: компаратор сообщает "тока много", но не
"почему". После срабатывания у оператора один бит, и постоянка ли виновата,
короткое в нагрузке или драйвер - гадать. gt_dcSat в журнале называет причину.

ОСТАНАВЛИВАТЬ ЛИ МОСТ ПО ЭТОМУ СОБЫТИЮ - вопрос открытый, решение за
эксплуатацией. Довод "за": в сетевом режиме постоянка в сеть нормирована
(3.1.8), и упор означает выход за норму. Довод "против": хронический случай
не аварийный, останов по нему уронит работающий прибор из-за того, что
когда-то подобрали mDCmax впритык. Если решат останавливать - строка одна,
grid_tie_fault(gt_dcSat) рядом с записью в журнал.


3.1.6 ДВА ИНТЕГРАТОРА В ПЕТЛЕ - ПОДТВЕРДИЛОСЬ, ВЫЛЕЧЕНО ПИ-РЕГУЛЯТОРОМ
   Прогон 24.09.2026, ниже.

Раздел писался как предсказание. С 24.09.2026 это измерение: звон есть, он
ровно такой, как посчитали, и лечится ровно тем, что здесь было предложено.
Хронология сохранена - сначала прикидка, потом замер, потом лечение.

Стендовый прогон 17.08 (раздел 6: mDC пришёл в -0.014885 при расчётных
-0.014881) проверил арифметику и знак. Динамику он не проверял, и вот почему.

В модели НЕ БЫЛО ветви намагничивания: ток первички был тождественно равен
n * ток вторички. То есть та самая физика, ради которой написан весь раздел
3.1, в симуляции отсутствовала. Постоянка загонялась через активное
сопротивление 0.5 Ом - объект первого порядка, который интегральный регулятор
отрабатывает гарантированно устойчиво.

С 23.09.2026 ветвь намагничивания в модели есть (plant_sim.txt), и разобранный
ниже объект-интегратор воспроизводится. Выводы этого раздела от того не
устарели - их стало чем проверить, не доводя до железа.

На железе объект другой. Постоянное напряжение на первичке не создаёт
установившийся ток - оно ИНТЕГРИРУЕТСЯ в поток, и ток нарастает как U*t/L_mag.
Объект сам по себе интегратор, а mDC -= kDC*iPri_av - второй интегратор.
Два интегратора в петле дают 180 градусов запаздывания, и демпфирует их только
активное сопротивление первички.

Прикидка при L_mag ~ 30 мГн и R_пер ~ 15 мОм (оценка для 3 кВт при 48 В,
ток намагничивания ~5 %):

    за период     dIa = mDC * Udc*T/L_mag = 32 А на единицу mDC
    петля         a*kDC = 32 * 0.0005 = 0.016
    колебание     ~1 Гц, zeta ~ 0.04, затухание ~4 с
    выброс Ia     ~2.5 А постоянки при отработке 0.48 В

2.5 А постоянного тока в первичке по потоку сравнимы с самим током
намагничивания. То есть контур в процессе "подавления" сам подводит сердечник
к насыщению, и так несколько раз с периодом около секунды.

L_mag и R не измерены, цифры оценочные. Но СТРУКТУРА вывода от них не зависит:
интегратор на интеграторе всегда даёт малое демпфирование.

Отдельно стоит отметить, что переключение нагрузки проверило ЗНАК контура

верную полярность датчика первички (gt.iSign), а отсутствие переворотов -
что затухание больше 0.5. Ради этого ступенька по нагрузке - лучший тест,
какой есть, и повторить его на железе надо первым делом.

ЧЕГО ЭТО НЕ ДОКАЗЫВАЕТ. Коэффициент посчитан по параметрам модели. Lmag и
Rwind на железе не измерены, и хотя оценка даёт почти тот же a, проверять
zeta на первом прогоне всё равно обязательно: смотреть iPri_av и mDC живьём
и убеждаться, что это УСТАНОВЛЕНИЕ, а не колебание. Если звон остался -
поднимать kDCp, а не опускать kDC.

Второе, чего модель не проверила: ВЕЛИЧИНУ выброса на железе. В модели
насыщения нет, и любой выброс проходит без последствий; на железе постоянка
в выбросе - это те же вольт-секунды в сердечник, и мерить её надо по таблице
3.1.1, а не по тому, вернулась ли она к нулю.

ПОЧЕМУ УМЕНЬШАТЬ kDC БЕСПОЛЕЗНО, ещё раз и теперь с доказательством. У
системы d2x/dt2 = -K*x частота равна корню из K, а затухание нулевое при
ЛЮБОМ K. Уменьшив kDC, получишь ровно то же незатухающее колебание, только
медленнее. Затухание появляется единственным способом - членом при первой
производной, то есть пропорциональной частью либо сопротивлением в объекте.


3.1.7 ДЫРА В GT_SYNC - ЗАКРЫТА 23.09.2026

Ниже описано, КАК БЫЛО. Дыры больше нет: dcAllow разрешает контур во всех
состояниях, где мост модулирует, включая GT_SYNC. Раздел оставлен потому, что
объясняет, зачем это состояние вообще важно, и задаёт порядок первого пуска
в конце.

Контур DC работал только в GT_RAMP и GT_RUN. Теперь совместим это с 3.5:
в GT_SYNC контактор разомкнут, но мост УЖЕ модулирует - специально, чтобы
к моменту замыкания разность на контактах была нулевой.

Что при этом происходит на железе. Вторичка ни к чему не подключена, Ib_amp = 0
физически, ошибка тока нулевая, PR молчит, мост выдаёт uSec = uGrid в холостой
трансформатор. Единственный ток в системе - ток намагничивания первички.
И вся асимметрия мёртвого времени интегрируется в поток без всякой
компенсации, потому что mDC заморожен на нуле: grid_tie_start() его обнуляет.

GT_SYNC длится минимум syncNeed = 25 периодов = 0.5 с, а при небыстром захвате
PLL сколько угодно дольше. По таблице 3.1.1 половины секунды хватает с запасом.

То есть самое опасное для сердечника состояние во всей последовательности -
это то, в котором контур подавления выключен. Причём выключен он, судя по
всему, из-за модели: при разомкнутом контакторе ток вторички в ней был нулевым,
а ток первички считался как n * ток вторички, то есть тоже нулевым, и
разрешать контур было бы бессмысленно. Артефакт симуляции, а не физики.

С 23.09.2026 артефакта нет: ток намагничивания в модели течёт и при разомкнутом
контакторе, как и на железе, - то есть уход потока в GT_SYNC теперь ВИДЕН.

Хорошая новость: iPri_av считается во ВСЕХ состояниях, dcAllow держит только
обновление mDC. Значит сырую постоянку видно и при выключенном контуре, и это
даёт порядок первого пуска:

    1. мост под током, ключи закрыты либо dcAllow снят - смотрим iPri_av.
       Это прямое измерение сырой постоянки без всякой обратной связи, и
       лучший момент её увидеть: нет тока нагрузки, который её маскирует.
       В сетевом режиме то же самое даёт GT_SYNC: вторичка ни к чему не
       подключена, и в первичке нет ничего, кроме тока намагничивания
    2. по этой цифре проверить оценку 0.48 / 0.048 В из 9.3 и заодно прикинуть
       реальный коэффициент a для 3.1.6
    3. дальше смотреть, как контур её убирает, и искать МЕДЛЕННЫЕ КОЛЕБАНИЯ
       около 1 Гц - предсказание 3.1.6, единственное непроверенное место

3.1.8 КАК С ЭТИМ БОРЮТСЯ В МИРЕ
   Добавлено 24.09.2026.

Задача не наша личная и давно имеет имя: flux walking, она же staircase
saturation - "лестничное" насыщение, когда поток каждый период поднимается на
ступеньку. В литературе по DC-DC она разобрана подробнее, чем в инверторной:
двухтактные и мостовые преобразователи страдают ею ровно по той же причине.

НОРМЫ. Для сетевого режима постоянка в сеть нормирована прямо:

    IEEE 1547     не более 0.5 % номинального тока
    IEC 61727     менее 1 % номинального действующего

Это про ток В СЕТЬ, то есть про вторичку, а не про наш контур намагничивания.
Но цифра полезна как ориентир порядка: 0.5 % от 20 А - это 0.1 А, и столько же
по 3.1.2 даёт одно только смещение нуля датчика вторички. То есть норма
примерно там же, где наши собственные погрешности, и выполнить её без контура
подавления нельзя.

ЧТО ДЕЛАЮТ. Пять подходов, по убыванию распространённости:

1. РАЗДЕЛИТЕЛЬНЫЙ КОНДЕНСАТОР последовательно с первичкой. Грубо и надёжно:
   постоянки физически нет. Платят размером и деньгами - при наших токах это
   серьёзная банка, - и получают резонанс с индуктивностью намагничивания,
   который приходится демпфировать.

2. ЗАМКНУТЫЙ КОНТУР ПО СРЕДНЕМУ ТОКУ - то, что у нас. Дёшево, ничего не
   добавляет в силовую часть, но медленно и, как разобрано в 3.1.6, ставит
   интегратор на интегратор.

3. НАБЛЮДАТЕЛЬ ПОТОКА ПО НАПРЯЖЕНИЮ. Поток считают интегрированием напряжения
   моста, а не ждут, пока вырастет ток. Быстрее принципиально: ток - это уже
   следствие. Требует измерения напряжения на обмотке и борьбы с дрейфом
   интегратора.

4. ПИКОВОЕ ТОКОВОЕ УПРАВЛЕНИЕ (current-mode). Классический ответ в мире DC-DC.
   ОТЛОЖЕНО В РЕЗЕРВ, разобрано отдельно в 3.1.9.
   Перекос потока проявляется как перекос ПИКОВ тока, и компаратор обрывает
   более длинный импульс раньше - коррекция получается потактовая,
   самопроизвольная, без всякого отдельного контура. Для нашей схемы это была
   бы смена метода модуляции целиком.

5. ЗАЗОР В СЕРДЕЧНИКЕ. Сдвигает колено, делает трансформатор терпимым к
   постоянке. Платят увеличенным током намагничивания и габаритом. Решение
   конструктора, не программиста.

ЧТО ИЗ ЭТОГО БЛИЗКО ЛЕЖИТ У НАС. Пункт 4 в чистом виде - это другая схема
управления, но его ИДЕЯ применима как измеритель: перекос положительного и
отрицательного пиков тока первички есть прямой признак одностороннего
насыщения (см. 3.1.1 - всплески идут через период, только в одной полуволне).

Считать это в CLA - четыре строки: держать max и min iPri_amp за окно и
отдавать разность модулей. И величина эта живёт ГОРАЗДО НИЖЕ порога
компаратора, то есть видит сердечник у колена задолго до того, как ток
станет аварийным. НЕ СДЕЛАНО, кандидат номер один, если после первого
прогона окажется, что gt_dcSat срабатывает слишком поздно.


3.1.9 РЕЗЕРВ: ПИКОВОЕ ТОКОВОЕ УПРАВЛЕНИЕ
   Отложено 24.09.2026. Не начато, взято на заметку.

Заготовка. Ничего из написанного ниже не сделано, и браться за это сейчас
незачем - контур mDC работает. Запись существует затем, чтобы через полгода
можно было поднять мысль с нуля, не восстанавливая ход рассуждений.

ЧЕМ ОН ОТЛИЧАЕТСЯ ОТ ВСЕГО ОСТАЛЬНОГО В ЭТОМ РАЗДЕЛЕ. Контур mDC лечит
СЛЕДСТВИЕ: даёт потоку уехать, ловит это в среднем токе за период и медленно
возвращает обратно. Пиковое токовое управление убирает САМ МЕХАНИЗМ -
асимметрия вольт-секунд просто не может накопиться, потому что модулятор её
не пропускает.

КАК РАБОТАЕТ. Такт ШИМ обрывается не по счётчику таймера, а по достижению
током заданного уровня. Если поток уехал, то в ту полуволну, куда он уехал,
ток достигает порога РАНЬШЕ - импульс обрывается раньше - вольт-секунды на
этой стороне уменьшаются - поток идёт назад. Коррекция каждый такт, сама,
без измерения среднего, без интегратора и без всякого вопроса об
устойчивости контура подавления. Именно поэтому в мире DC-DC двухтактные и
мостовые преобразователи делают в токовом режиме по умолчанию: flux walking
там лечится не регулятором, а выбором модуляции.

ЧТО УЖЕ ЕСТЬ НА ПЛАТЕ - ради этого запись в основном и нужна, половина
работы сделана под другую задачу:

    - CMPSS2 уже сравнивает ток первички с порогами DACH/DACL,
      их ставит currentLimit() в myADC.c;
    - уже заведён путь в силовую часть: EPWM X-BAR MUX02 -> TRIP5 -> DCBH
      -> DCBEVT1 (раздел 10.4);
    - DAC компаратора уже умеет везти СИНУС, а не константу: ровно это
      делает DBG_SIN_DAC на CMPSS1 (10.1). То есть приём отработан.

ЧЕГО НЕ ХВАТАЕТ, три вещи:

    1. DCBEVT1 сейчас в режиме ONE-SHOT - защёлка аварии. Для токового
       режима нужен CYCLE-BY-CYCLE: событие не защёлкивается, а обрывает
       импульс до конца периода и снимается на границе. Это смена режима
       DC-события, а не схемы.
    2. В DAC должна ехать УСТАВКА тока (синусоида), а не постоянный порог.
       Писать каждый такт из обработчика - путь проторён.
    3. Наклонная компенсация. Классическая болезнь пикового режима: при
       заполнении выше половины появляется субгармоническая неустойчивость
       на половине частоты ШИМ. Лечится компенсирующим наклоном, и у CMPSS
       для этого есть встроенный генератор наклона.

КОНФЛИКТЫ, КОТОРЫЕ ПРИДЁТСЯ РЕШАТЬ:

    - CMPSS2 сейчас держит ОТСЕЧКУ по току первички. Если его DAC займёт
      уставка, фиксированный порог защиты с этого модуля уйдёт, и защиту
      первички надо будет переселить.
    - Модуль один, а порогов нужно два: уставка и авария. Верхний и нижний
      компараторы CMPSS уже заняты - они несут две полярности переменного
      тока через CTRIPH_OR_L (10.4).

ГРАНИЦЫ ПРИМЕНИМОСТИ, и это главное ограничение мысли. Пиковый режим делает
мост ИСТОЧНИКОМ ТОКА.

    в сетевом режиме   ложится естественно: мост и так источник тока, а
                       PR-регулятор вместо напряжения задавал бы уставку
    в АИН              не работает сам по себе: там мост - источник
                       напряжения на нагрузку, и понадобился бы внешний
                       контур напряжения поверх

Отсюда вывод для резерва: ЭТО НЕ ЗАМЕНА контуру mDC, а способ снять с него
нагрузку в сетевом режиме. В АИН - а первым с железом включат именно его -

КОГДА БРАТЬСЯ. Если на железе выяснится, что mDC не справляется (упирается в

ступенька по нагрузке отрабатывается за секунду без звона (3.1.6), повода
нет.


3.2 ЗАПАС ПО ИНДЕКСУ МОДУЛЯЦИИ - УЗКОЕ МЕСТО СХЕМЫ

Чтобы получить 311 В пика на вторичке, нужно

    n * m * Udc >= 311 В   плюс падение на рассеянии при рабочем токе

При n = 7 и просевшем под нагрузкой АКБ 42 В получается 0.95*7*42 = 279 В.
Это меньше 311 - отдача невозможна в принципе. Регулятор упрётся в потолок
на пиках синусоиды, а форма тока испортится.

Коварство в том, что при 48 В всё работает, а при разряде АКБ ломается,
причём в пиках - то есть выглядит как искажение, а не как отказ.

Поэтому упор считается и превращается в аварию, а не игнорируется:

    satCount   тактов в упоре за текущий период сети
    satLast    он же за прошлый (dbg)
    satLimit   сколько допустимо, по умолчанию 10 из 100

Если ловишь gt_mSat - смотри не на коэффициенты регулятора, а на Udc и на n.
Коэффициент трансформации выбирается по МИНИМАЛЬНОМУ напряжению АКБ под током,
с запасом 10-15 %.

ЭТОТ ЗАПАС ТЕПЕРЬ СЧИТАЕТСЯ САМ, и считать его в уме больше не нужно. С
25.09.2026 у прибора есть паспорт силовой части (my_Files/power_par.txt), а в
нём два выведенных числа:

    mNom    требуемый индекс модуляции на холостом ходу
    mLoad   он же при номинальной АКТИВНОЙ нагрузке

Больше gt.mMax - схема уставку не вытянет, и видно это ДО включения моста.
Ни одного провода для проверки не нужно: вписал паспорт чужого инвертора -
получил ответ. Проверять при этом надо на ИНДУКТИВНОЙ нагрузке (11.8), а её
формула не ловит - для неё гоняют модель.

3.3 UDC ТОЛЬКО МГНОВЕННЫЙ

Однофазный мост тянет из АКБ мощность, пульсирующую с частотой 100 Гц.
Напряжение АКБ качается с той же частотой. Прямая связь обязана видеть
мгновенное значение - иначе пульсация вылезет прямо в ток. Vin_rf
(сглаженный) здесь использовать нельзя.

3.4 ПУСК В МАКСИМУМЕ НАПРЯЖЕНИЯ

Автомат ждёт четверть периода после нуля напряжения и только потом замыкает
контактор. Поток - интеграл напряжения, старт с максимума даёт нулевое
начальное смещение потока и убирает бросок намагничивания.
Отсчёт - gt.startDelay, взводится при наборе syncNeed.

3.5 КОНТАКТОР И ХОЛОСТОЙ ХОД ПЕРЕД ЗАМЫКАНИЕМ

Это выяснилось на первом же прогоне и стоило аварии gt_overIpri.

Если в GT_SYNC держать мост закрытым (m = 0), а потом замкнуть контактор,
то в момент замыкания на индуктивности рассеяния оказывается ПОЛНОЕ сетевое
напряжение: 272 В на 8 мГн дают 6.8 А за такт, за четверть периода 170 А.
Это короткое замыкание, и защита ловит его совершенно правильно.

Поэтому порядок такой:

    GT_SYNC   контактор РАЗОМКНУТ, но мост уже модулирует. Контур тока
              работает с нулевой уставкой, то есть активно держит ток в нуле,
              а значит напряжение моста само подстраивается под сетевое.
    переход   к моменту замыкания разность на контактах нулевая
    GT_RAMP   контактор замкнут, уставка растёт от нуля

Переход получается безударным: m не прыгает, PR не дёргается.

Флаг gt.acContactor пока живёт только в модели - GPIO под реле не выделен.
Когда появится, дёргать реле надо ровно там, где сейчас ставится этот флаг.


4. МОДУЛЯЦИЯ: ОНА УЖЕ ТРЁХУРОВНЕВАЯ
--------------------------------------------------------------------------------

    CMPA_A = TBPRD*(1-m)/2
    CMPA_B = TBPRD - CMPA_A = TBPRD*(1+m)/2

Режим UP_DOWN, UP_CMPA -> HIGH, DOWN_CMPA -> LOW, значит доля высокого уровня
плеча = 1 - CMPA/TBPRD. Отсюда dA = (1+m)/2, dB = (1-m)/2 и U_AB = m*Udc.

Теперь неочевидное и важное. Окна открытого состояния ОБОИХ плеч
отцентрированы по вершине счётчика. При m > 0 окно плеча B уже окна плеча A
и целиком в него вложено. Значит U_AB принимает только два значения: 0 и +Udc.
При m < 0 - только 0 и -Udc.

Это трёхуровневая (unipolar) модуляция, и частота пульсации тока вдвое выше
несущей: 10 кГц при ШИМ 5 кГц. Для трансформатора это заметно лучше
двухуровневой. Соотношение CMPA_A + CMPA_B = TBPRD ломать нельзя - потеряешь
это даром доставшееся свойство.

Сравни со старым sine_invertor2: там CMPA_B = tbperiod - CMPA_A, где
tbperiod = gain/2048*pwm_period, то есть НЕ равно TBPRD. Поэтому модулятор
написан заново, а не переиспользован.

Это то, чего в U220_sync.txt прямо не хватало (см. там раздел 1, "Откуда ждать

значениях, и мост продолжит выдавать синусоиду по памяти. В автономном режиме
это просто странно, а в сеть - недопустимо.

5.2 ПОЧЕМУ АВАРИЯ ДЕЛАЕТСЯ В ДВА ЭТАПА

grid_tie_fault() вызывается из прерывания и делает там только быстрое:
ставит m = 0 и оставляет заявку. Само закрытие IGBT и запись в журнал
происходят в grid_tie_background(), из фона.

Причина не в скорости, а в корректности:
    - IGBT1_Disable() / IGBT2_Disable() делают EINT внутри себя. Вызов
      из ISR разрешил бы вложенные прерывания посреди обработчика.
    - RegisterSessionEvent() лезет в журнал и историю ошибок.

При этом выход обесточивается СРАЗУ: m = 0 означает, что оба плеча стоят
на 50 %, напряжение моста равно нулю уже со следующего периода ШИМ, то есть
через 200 мкс. Фон только доводит дело до конца.

6.1 ЧЕМ СМОТРЕТЬ ФОРМУ

Отдельные значения в Expressions показывают состояние, но не форму. Для формы
есть два инструмента, и они для разного.

КОЛЬЦЕВОЙ БУФЕР - основной, для модели. Четыре массива в RAMGS1, заполняются
в конце grid_tie_step(), по GT_TRC_LEN = 200 отсчётов = два периода сети:

    gtTrcIref[]   заданный мгновенный ток, А
    gtTrcIb[]     измеренный ток вторички, А
    gtTrcIa[]     измеренный ток первички, А
    gtTrcM[]      индекс модуляции

    gtTrcRun = 1  пишем по кругу непрерывно (значение по умолчанию)
    gtTrcRun = 2  снимок по событию, ждущая развёртка осциллографа
    gtTrcRun = 0  стоп

    gtTrcIdx      куда пишется следующий отсчёт

СНИМОК (с 09.10.2026). Взведённый, он пишет по кругу и ждёт события: смены
gt.Iset, gt.Iq или gt.State. Авария - тоже событие, это переход в
GT_FAULT. Чем запущен последний снимок - gtTrcWhy: 1 состояние, 2 Iset,
4 Iq (биты складываются).

Переход RUN <-> RAMP событием не считается: на первом нуле сети после
смены уставки автомат только уходит RUN -> RAMP, а Iset трогает на
следующем, через период. Запуск по нему увозил ступеньку на отсчёт 150.

Почему Iset, а не уставка IsetRef: уставка доходит до тока только на
переходе сети через ноль, рампой в grid_tie_onGridZero(), на 0..20 мс
позже нажатия. Первый вариант запускался по IsetRef - событие стояло на
отсчёте 50, а ступенька уезжала вправо: в проверочном опыте на отсчёт
166 из 200. Запуск по Iset ставит на отсчёт 50 саму ступеньку тока. После события дописывается GT_TRC_LEN - GT_TRC_PRE = 150 тактов и
запись встаёт: gtTrcDone = 1. Фон (grid_tie_background) поворачивает все
четыре кольца так, что отсчёт 0 - самый старый, и только потом сбрасывает
gtTrcRun в 0. Итог: 50 тактов (10 мс) до события, 150 (30 мс) после,
событие ровно на отсчёте 50.

Порядок опыта: "Трасса" = снимок, затем само возмущение - когда удобно,
хоть через минуту. Строка вернулась в "стоп" - снимок готов, обновить
график. Предыстория набирается 10 мс после взвода; руками быстрее не успеть.

Событие сравнивается с прошлым тактом, а не ловится в местах смены:
состояние меняют автомат, grid_tie_fault() и команды по CAN.

Рампа (IsetSlew) идёт шагами раз за период, и снимок ловит ПЕРВЫЙ шаг.
Чтобы снять отклик контура на настоящую ступеньку, IsetSlew_x100 ставится
на максимум (5000) на время опыта: скачок проходит за один период. Всю
рампу целиком, на секунды, 40 мс окна не покажут при любой настройке.

ПРЕЖНИЙ СНИМОК (до 09.10.2026) писал 40 мс от самой команды, поэтому
ступеньку, поданную вторым нажатием, не ловил в принципе. И индекс он не
сбрасывал: буфер заполнялся от текущего места до конца, остальное
оставалось от старой записи и выглядело как настоящая кривая.

В CCS 20 и новее (Theia) окно другое, чем в прежнем Eclipse-CCS с его
Tools -> Graph -> Single Time. Это "Create a New Graph":

    Capacity          200 (GT_TRC_LEN; больше - захватит чужую память)
    Start Addresses   имя массива, без & и индекса; строк можно несколько,
                      кривые лягут на один график. Тип данных - 32-bit
                      float, у каждой строки свой значок настроек

Панель управления графиком маленькая и сидит в правом верхнем углу, её
легко не заметить. Обновление работает на бегущем процессоре, останавливать
его не нужно (а на железе с открытыми ключами и нельзя).

Раскладка по графикам: gtTrcIref и gtTrcIb - на один. При работающем
контуре они совпадают до долей ампера, и одна кривая закрывает другую;
gtTrcIa рядом с ними растянул бы шкалу в n раз, и расхождение ушло бы в
толщину линии. gtTrcIa - на свой, gtTrcM (-1..+1) - тоже на свой.

Осциллограф для этого не нужен вообще: на модели ток - это число в ОЗУ, и
вывод его через ЦАП с последующим замером добавил бы два преобразования
между наблюдателем и правдой.

Буферы лежат НЕ в .bss: он привязан к одному блоку RAMLS5 (0x800 слов), и
1600 слов массивов кладут линковку. Отсюда #pragma DATA_SECTION в "ramgs1" -
тот же приём, что у ErrHistory в KSP/Errors.c.

ОТЛАДОЧНЫЙ ЦАП - для железа. Аналоговых выходов у кристалла два (см. 10.1),
и DACA занят имитацией сети. Остаётся нижний ЦАП CMPSS1, пин A1/B7/D11
(HSEC 11), при DBG_SIN_DAC = 1. Что на него идёт - выбирается на живой цели:

    dacDbgSrc = 0   dacb, синусоида ШИМ (как было)
    dacDbgSrc = 1   gt.Ia_amp, ток первички
    dacDbgSrc = 2   gt.Ib_amp, ток вторички
    dacDbgSrc = 3   gt.m, индекс модуляции
    kDacDbg  50.0   код на ампер: 2048/40 -> шкала +-40 А
    dacDbg          dbg что реально ушло на пин

dacb как ЧИСЛО нужен всегда - по нему идёт подстройка фазы в
INT_U220_zero_ECAP_ISR, - но это никак не связано с пином. Забрать вывод
под ток можно, контур синхронизации этого не заметит.

Оговорки. Обновление 5 кГц: на 50 Гц это 100 ступенек за период, форма видна
хорошо, но всё быстрее ~1 кГц осциллограф покажет как артефакт дискретизации.
Выход небуферизованный и слабый - пробник 10:1 нормально, 1:1 может подсадить.
Пин A1/B7/D11 - это ещё и вход B7, куда по нынешнему syscfg смотрит Ib
(открытый вопрос 7.3); на стенде датчика нет и это не мешает.

Смысл ЦАПа появляется именно на железе: он показывает, что МК ДУМАЕТ о токе,
и сверка этого с реальным током по токовым клещам - единственный способ
проверить kadc.Ia и gt.iSign.


6.2 ТЕЛЕМЕТРИЯ В WSCOPE - НЕПРЕРЫВНАЯ ЗАПИСЬ

Третий инструмент, и единственный, который даёт ДЛИННУЮ запись. Буфер 6.1
показывает два периода, телеметрия - сколько угодно. Для медленных вещей
(звон контура DC с периодом около секунды, 3.1.6) только она и годится.

Кадров три, и выбираются они полем "F2 Кадр" в окне (команда CAN 1001).
Все идут ID 103 через буфер 1, все отправляются из INT_myADCB_1_ISR.
Третий, F3_grid, - контур тока изнутри, описан после F1_convertor.
Набор Kadr60 в том же поле - не лента, а медленная запись кадра 140; он
идёт другим путём и описан после F3_grid.

F3_convertor - ОСНОВНОЙ, 16 слов, 32 байта, DLC 13. Везёт весь контур тока и
все шесть измеряемых величин тракта разом, выбирать ничего не надо:

    слово  величина        масштаб   тип   что это
      0    phaseErr        1e-4      i16   ошибка детектора фазы
      1    uGrid           0.1 В     i16   сеть, приведена ко вторичке
      2    iref            0.01 А    i16   заданный мгновенный ток
      3    iSec_amp        0.01 А    i16   ток вторички
      4    iPri_amp        0.01 А    i16   ток первички

      7    uBat_volt       0.1 В     i16   напряжение звена, ИЗМЕРЕННОЕ
      8    mDC             1e-5      i16   поправка постоянной составляющей
      9    dacb            коды      u16   опора детектора фазы
     10    uSec_volt       0.1 В     i16   выход инвертора        (23.09.2026)

правки. Счётчик тактов переехал с 11-го слова на 15-е, и иначе нельзя: он
ОБЯЗАН быть последним, см. ниже.

СЛОВО 7 - ИЗМЕРЕНИЕ, А НЕ ПРЕДСТАВЛЕНИЕ КОНТУРА. Там стояло gt.Udc, и это была
ошибка: gt.Udc есть то, ЧЕМ КОНТУР ДЕЛИТ, и при UdcSrc = 0 туда подставляется
константа UdcFixed - в ленту ехала бы прямая линия вместо сигнала датчика.
Канал uBat преобразуется каждый такт независимо от режима и от ключей, и в
ленте место именно ему. Исправлено 23.09.2026.

ДВА СЛОВА ОСВОБОДИЛИСЬ в тот же день. Ушли u220_kod - сырые коды того же
канала, который уже едет вольтами в слове 1, - и вторая копия напряжения АКБ.
Отдавать место шине не стали: четырнадцати слов у CAN FD нет, ближайшая длина
вниз - двенадцать, и это стоило бы ещё двух каналов. Одно слово тут же заняла
мгновенная мощность, второе - поправка контура выходного напряжения острова
(25.09.2026, вместе с появлением самого контура). Свободных слов в кадре больше
нет.

СЛОВО 14 - ПОПРАВКА КОНТУРА U ОСТРОВА, 0.1 В rms. В ленте она нужна рядом с
uSec_volt (слово 10) и m (слово 5): втроём они и отвечают на вопрос, почему
напряжение стоит не там, где заказано. Растёт вместе с нагрузкой - контур
работает; стоит на потолке uOutCorMax - уставка недостижима, см. gt_uOutSat.

СЛОВО 13 - МГНОВЕННАЯ МОЩНОСТЬ на выходе инвертора, произведение тех же двух
каналов, из которых CLA считает активную. Усреднив эту кривую за период сети,
получите ровно pSec - то число, что стоит в окне и в слове 17 кадра 140.
Пульсация двойной частоты в ней не артефакт, а физика однофазного моста:
произведение двух синусоид одной частоты даёт постоянную часть плюс колебание
на 100 Гц размахом от нуля до двойного среднего. Именно её мост тянет из АКБ,
и ради неё gt.Udc берётся мгновенным (раздел 3.3). При реактивной нагрузке
часть периода кривая уходит в минус - это возврат энергии из индуктивности.

СЛОВО 12 - НЕ ДАТЧИК. Ток намагничивания отдельно не измеряется, его и не
существует как отдельной цепи: прошивка считает iПерв/n - iВтор и приводит ко
вторичке. На модели это в точности sim.iMag, на железе - настоящий ток
намагничивания. Именно по нему виден уход потока в сердечник (раздел 3.1),
и до 23.09.2026 наблюдать его было нечем.

F3_grid - КОНТУР ТОКА ИЗНУТРИ, 16 слов, 32 байта, DLC 13; код 6 команды 1001
(5 занят медленным кадром). Заведён 09.10.2026. F3_convertor показывает, ЧТО
вышло; этот набор - ПОЧЕМУ. Карта каналов - bin/Wscope/F3_grid.ini:

    слово  величина        масштаб   что это
      0    gt.iref         0.01 А    задание, мгновенное
      1    iSec_amp        0.01 А    ток в сеть
      2    gt.ierr         0.01 А    ошибка контура, 0 вне RAMP/RUN
      3    gt.uGrid        0.1 В     прямая связь по сети
      4    PR out          0.1 В     выход регулятора: Kp*err + x1
      5    PR x1           0.1 В     резонатор
      6    gt.uSec         0.1 В     заказано мосту: uGrid + out
      7    uSec_volt       0.1 В     получено на выходе инвертора

      9    mDC             1e-5

Скачок читается цепочкой IsetRef -> Iset -> iRef -> iSec: нажали, рампа
пошла (раз за период, на переходе сети через ноль), задание, ток. В слове 10
до 09.10.2026 стоял gt.Udc, но при UdcSrc = 0 это константа UdcFixed -
прямая линия; датчик звена - Vin в F3_convertor. Тогда же движок Load1
потерял подпись Iref: в ленте iRef уже занят мгновенным заданием, а Wscope
и осциллограф регистр в именах не различают. Теперь на нём "Iзад", полное
имя IsetRef - во всплывающей подсказке. Моторные режимы движка (скольжение,
Iq, gain, RPM), нижняя кнопка RPM/Поле и симметрия Load1 -> Load2 убраны:
они слали команду 73 в motors[0]->ref.sAbs, которого никто не читает.

uSec при замкнутом контакторе стоит на сети и показывает её же. Мёртвое
время и падение на ключах ложатся внутри трансформатора, на рассеянии, и
видны в ierr и prOut, а не в uSec. Он нужен в слежении (uSec - uGrid - это
ошибка контура напряжения) и в момент замыкания контактора.

Регулятор в словах 4..5 - тот, что считается СЕЙЧАС: в GT_SYNC это контур
напряжения prv, в RAMP/RUN - контур тока pr. Оба выдают вольты на вторичке,
так что смысл кривых при замыкании контактора не меняется.

Вне контура (OFF, FAULT, слежение при закрытых ключах) gt.ierr и gt.uSec
обнуляются в grid_tie_step(). До 09.10.2026 они хранили последнее значение -
в ленте это была бы прямая линия, неотличимая от сигнала.

Все слова идут через TEL_I16() с упором на краях шкалы: при ошибке или
аварии ток и выход PR легко выходят за int16, а прямое приведение float на
C28x даёт не упор, а что придётся.

В Motor_Control разбор общий с F3_convertor (Kadr60.cs, SplKadr.cs): длина
та же, счётчик там же, различаются наборы только картой каналов. В списке
"F2 Кадр" F3_grid стоит ПОСЛЕДНИМ, после Kadr60, - номер выбора хранится в
настройках по индексу, и вставка в середину пересадила бы на чужой набор.

Kadr60 - НЕ ЛЕНТА, А МЕДЛЕННАЯ ЗАПИСЬ: кадр 140 целиком, 32 слова, в файл.
Переделан 11.10.2026. До того под этим именем жил моторный кадр 131 -
константы 1, 2, 3 и счётчик по таймеру T1, - а в файл Motor_Control писал
29 моторных величин, которых в приборе нет. Теперь это ход режима на минуты
и часы: действующие токи и напряжения, мощности, частота сети, постоянка в
трансформаторе, запас по m, автомат и аварии.

Отдельного кадра под запись НЕТ, и это решение, а не недоделка: он вёз бы
те же слова вторым экземпляром. Кадр 131, таймер T1, Send_kadr60() и файл
KSP/Kadr60.c удалены, буфер 3 свободен. Пишется сам кадр 140 - тот, что
показывает окно: прибор шлёт его раз в 50 мс по таймеру T0, пока нажато
"Подключить".

Ради записи в кадре одно новое слово - 31-е, K60cnt, счётчик отправленных
кадров. По его изменению Motor_Control считает запись готовой, поэтому он
ОБЯЗАН быть последним; слова 26..30 остаются в резерве. Скачок счётчика в
записи больше чем на единицу - кадр потерян в пути.

Что из этого следует:

  - в файле ровно то, что на экране, разойтись им негде;
  - слова 4..7 несут набор, выбранный в окне (teleSel). Для длинной записи
    держать rms: коды и мгновенные, взятые раз в 50 мс, - не сигнал, а
    биения с 50 Гц. Какой набор шёл, в записи говорит канал teleSel;
  - в аварии измеренные слова заморожены, как и в окне: прямая линия после
    state = 4 - это заморозка, а не работающий мост. Счётчик заморозка не
    трогает, запись в аварии идёт;
  - период 50 мс из окна не меняется. K60per и команда 1 остались (поле в
    окне ждёт ответа), но читать K60per больше некому;
  - код 5 команды 1001 ничего не включает, только гасит быструю ленту.

Имена каналов в bin/Wscope/Kadr60.ini намеренно НЕ те, что в быстрых лентах
(iSecTel, а не iSec): Wscope хранит размах кривой по имени канала в сырых
кодах, один на все шаблоны, а в ленте это мгновенный ток вокруг нуля, в
кадре 140 - обычно действующий, ровная линия.

ЦЕНА СЛОВ 4..7 КАДРА 140: токи 0.01 А, напряжения 0.1 В. Токи до 11.10.2026
шли по 0.1 А, и при пяти амперах это два процента: действующий ток у границы
округления прыгал в окне и на графике между 5.2 и 5.3. Напряжениям сотые не
дать: действующему они влезли бы, а мгновенному нет - потолок слова стал бы
327 В при амплитуде сети 325 В. Менять цену надо в трёх местах разом:
REF_Kadr.c, Parse140 в Oleg/Kadr60.cs и Kadr60.ini; по кадру старую прошивку
от новой не отличить.

В Motor_Control: Parse140 (Oleg/Kadr60.cs) кладёт все 32 слова в ccs.k60, а
счётчик в ccs.k60Cnt берёт ТОЛЬКО при выбранном наборе Kadr60 - иначе каждый
кадр 140 вставлял бы лишний отсчёт в быструю запись. SplKadr.cs отдаёт слова
в файл как есть. Живой осциллограф набор не рисует - он слушает только
кадр 103.

F1_convertor - экономный, 4 слова, 8 байт, DLC 8. Три величины на выбор
плюс счётчик. Нужен, когда шину жалко или когда хватает трёх кривых:

                 канал 0          канал 1          канал 2
    telSrc = 0   cmpaA    u16     cmpaB    u16     duty*1000     i16
    telSrc = 1   iref*100 i16     Ib_amp*100 i16   m*10000       i16
    telSrc = 2   Ia_amp*100 i16   uGrid*10 i16     mDC*100000    i16
    telSrc = 3   dacb     u16     u220_kod u16     phaseErr*10000 i16

telDiv (прореживание, слать каждое N-е прерывание) ОБЪЯВЛЕН, НО НЕ РЕАЛИЗОВАН:
строки, которая бы его читала, в коде нет. Значение менять бесполезно.

ЗНАКОВОСТЬ - ОТДЕЛЬНЫЕ ГРАБЛИ, И НА НИХ УЖЕ НАСТУПИЛИ (20.08.2026). Прежние
каналы cmpaA/cmpaB были беззнаковые, и настройки Wscope это помнят. Все новые
каналы, кроме telSrc = 3, - ЗНАКОВЫЕ. Беззнаковый разбор превращает мелкое
отрицательное значение в число под 65535, и график встаёт частоколом до потолка.
Выглядит как настоящая помеха в сигнале, лечится строкой в ini.

Хуже всего telSrc = 3: там в ОДНОМ кадре два беззнаковых канала (dacb, u220_kod -
это сырые коды АЦП 0..4095) и один знаковый (phaseErr). Тип задавать поканально,
на кадр целиком не получится.

Масштабы ЗАШИТЫ В КОД, не в переменные. Приёмная сторона декодирует по
фиксированной таблице, и масштаб, который покрутили в отладчике и забыли,
даст на графике молча неверные числа - худший вид ошибки измерения.

telSrc = 0 оставлен по умолчанию, но в сетевом режиме он наполовину мёртв:
duty считает sine_invertor2(), а её при gridMode = 1 никто не зовёт, так что
третий канал показывает застывшее значение.

ПОСЛЕДНЕЕ СЛОВО - sineTick, счётчик тактов, и место у него не произвольное.

Send_mbox_FD молча пропускает кадр, если буфер занят передачей предыдущего.
В ленте пропуск неотличим от настоящей паузы в сигнале: Wscope нарисует сжатый
по времени участок, и это будет выглядеть как реальная динамика. По разрывам
sineTick пропуск виден сразу. Никогда не строить график по номеру отсчёта -
только по tick.

А в ПОСЛЕДНЕМ слове он потому, что Motor_Control считает запись готовой именно
по изменению последнего слова (CanaAsync.cs: if (_cntRef == ccs.k60Cnt) return).
Величина, способная повториться у соседних отсчётов, на этом месте заставит
запись стоять - лента поползёт вместо того, чтобы идти. Это же написано в
шапке bin/Wscope/F3_convertor.ini.

ПОЧЕМУ ЖИВОЙ ОСЦИЛЛОГРАФ И WSCOPE ПОКАЗЫВАЮТ ОДНО И ТО ЖЕ ПО-РАЗНОМУ. На этом
легко запутаться, и один раз уже запутались (04.10.2026).

Живой осциллограф в Motor_Control ставит отсчёт на ось по ЕГО ТАКТУ. Пропал
кадр - на его месте остаётся пустое место, и линия рвётся: в этой точке
измерения нет, и рисовать там нечего. Рвутся при этом ВСЕ кривые разом - теряется
кадр целиком, а не отдельный канал.

Wscope строит по НОМЕРУ ОТСЧЁТА. Следующий отсчёт встаёт вплотную к предыдущему,
и провал закрывается сам собой: график выглядит безупречно, просто участок слегка
сжат по времени. Данных в обоих случаях ровно столько же - разница только в том,
что один инструмент о пропуске говорит, а другой молчит.

Отсюда и ощущение "у осциллографа разрывы, а в Wscope их нет". Их нет видно, а не
нет вовсе.

ПОЧЕМУ РОВНО ОДИН ТАКТ, А НЕ ДВА, хотя 140-й занимает эфир 247 мкс при такте

    0 мкс     кадр 140 начал передачу

"макс 2" в строке состояния осциллографа - это и есть подтверждение модели до

Решено оставить как есть: 0.4 % одиночных пропусков на форме тока не видны, а

СКОЛЬКО ЭТО ЗАНИМАЕТ ШИНЫ. MCANA тактируется от SYSCLK без деления
(device.c: SYSCTL_MCANCLK_DIV_1), то есть 150 МГц:

    номинал   prescaler 6,  бит = 1+18+6 = 25 tq  ->  1.0 Мбит/с
    данные    prescaler 2,  бит = 1+22+7 = 30 tq  ->  2.5 Мбит/с

Кадр ID 103 (11-битный ID, FD+BRS). Арбитраж, ACK, EOF и IFS идут на
номинальной скорости и стоят ~29 бит = 29 мкс при любом размере; данные - на
своей:

    F1, 8 байт     ~92 бита  (64 данных + DLC, CRC17, стаффинг)   37 мкс
                   итого                                        ~66 мкс   33 %
    F3, 32 байта  ~290 бит   (256 данных + DLC, CRC21, стаффинг) 116 мкс
                   итого                                       ~145 мкс   72 %

Проценты - от периода такта 200 мкс при 5 кГц. Расширение кадра с 24 до
32 байт 23.09.2026 подняло загрузку с 59 до 72 %: запас есть, но он уже не
такой, чтобы о нём не думать. Инструмент контроля - telDrop, см. ниже.

Медленный кадр ID 140 - это 64 байта, то есть ~247 мкс в эфире, ДОЛЬШЕ периода
такта. Арбитраж тут не помогает: он решает, кто начнёт передачу, а начатую не
прерывает. Идёт он от таймера T0 каждые 50 мс и командой 1001 не выключается -
send_REF_kadr() гейтится только sbit.bit.connect. По расчёту это должно стоить
один отсчёт из 250, порядка 0.4 %.

Размер кадра 140 проверен по исходнику 20.08.2026 и равен именно 64 байтам:
MCAN_initTxBuffer(2, 140, 15, ...) даёт DLC 15, tele[32] уходит целиком через
Send_mbox_FD(2, tele, 32), txBufElemSize = 7 (64 байта), а подмены DLC на лету
для буфера 2 нет - MCAN_setFastDLC трогает только буфер 1.

"ИЗМЕРЕНО 20.08.2026: telDrop = 0" - ЭТО БЫЛО НЕ ИЗМЕРЕНИЕ. Счётчик завели,
но строки, которая бы его увеличивала, в коде не было ни одной: переменная
просто лежала в нуле с момента загрузки, и смотреть на неё значило смотреть
на константу. Обнаружено и исправлено 23.09.2026, теперь считает по-настоящему.

Вывод ниже от этого не изменился - он держится не на счётчике, а на разборе
того, кто вообще выходит в эфир, - но проверить его заново стоит.

Кадр 140 в сеансе Wscope просто не выходит в эфир. send_REF_kadr() гейтится
условием sbit.bit.connect, а этот бит взводится ровно одним местом - командой
CAN 1001 case 2, "нажата Кнопка Подключить" в основном UI (MBOX28.c). Wscope
только слушает и эту кнопку не нажимает. Значит в чистом сеансе телеметрии
на шине ОДИН быстрый кадр, треть загрузки, и терять нечего.

Механизм в расчёте описан верно, ошибочной была посылка: я считал, что 140-й
идёт всегда, раз таймер T0 запущен из main(). Таймер-то запущен, но гейт стоит
не на нём.

СЛЕДСТВИЕ, КОТОРОЕ ВАЖНО ПОМНИТЬ. Потери появятся в СОВМЕЩЁННОМ сеансе -
когда основной UI подключён и одновременно идёт лента в Wscope. Тогда 140-й
оживает, и оценка 0.4 % снова в силе. Проверяется мгновенно: нажать
"Подключить" и посмотреть, пошёл ли telDrop.

    telDrop растёт, в ленте дырки  -> не успевает шина или буфер
    telDrop = 0,     в ленте дырки -> теряет адаптер или приложение

ЧТО ОСТАЛОСЬ НЕОБЪЯСНЁННЫМ. По наблюдению Олега пропуски появляются, если
поднять sineB.resolution выше 100. Разрешение задаёт частоту такта: 100 -> 5 кГц
и период 200 мкс, 150 -> 7.5 кГц и 133 мкс. Но кадр занимает ~66 мкс, а других
кадров на шине в сеансе Wscope нет вообще (см. выше) - значит до разрешения
примерно 250 шина не при чём совсем. Кандидаты: время самого обработчика
(смотреть sine_Time), BRS, который мог не примениться (тогда кадр идёт целиком
на 1 Мбит/с, это ~120 мкс и порог сдвигается вниз), и приёмная сторона.
МЕХАНИЗМ НЕ УСТАНОВЛЕН.

Теперь это наконец меряется: поднимать sineB.resolution до тех пор, пока
telDrop не начнёт расти. Растёт - виноват МК (шина или обработчик); стоит в
нуле, а дырки в ленте есть - виноват приёмник. Раньше этот опыт поставить было
нечем - счётчик молчал не потому, что пропусков не было, а потому, что его
никто не увеличивал.

Оценки порога, которые стоит пересчитать под расширенный кадр: 145 мкс в эфире
против 200 мкс такта означают, что шина упрётся уже при resolution около 138
(период 145 мкс). Прежние 66 мкс давали запас до 250. То есть наблюдение Олега
про "выше 100 появляются пропуски" теперь имеет и чисто шинное объяснение -
проверить в первую очередь именно его.

ЕСЛИ ЗАХЛЁБЫВАЕТСЯ ПРИЁМНАЯ СТОРОНА: 5000 кадров в секунду должны пролезть
через адаптер USB-CAN и разобраться в приложении. Лечится telDiv. При
telDiv = 2 остаётся 50 отсчётов на период сети - для формы тока 50 Гц всё
ещё с избытком, теряется только детализация масштаба ШИМ.

ЧЕМ ЭТО ОТЛИЧАЕТСЯ ОТ БУФЕРА 6.1. Буфер берёт срез одного такта целиком
и без потерь - там нет ни пропусков, ни квантования в int16. Телеметрия
берёт длину. Для проверки формы тока и упора по m - буфер; для медленных
процессов и для всего, что надо показать не через отладчик, - телеметрия.

7. ЧТО ОБЯЗАТЕЛЬНО СДЕЛАТЬ ПЕРЕД ЖЕЛЕЗОМ
--------------------------------------------------------------------------------

7.1 ТРИГГЕР ADCB - СДЕЛАНО 17.08.2026

Была ошибка с самого начала проекта: ADCB SOC0/SOC1 (Ia, Ib) запускались
от ADC_TRIGGER_EPWM2_SOCA, а у epwm2 триггер SOCA включён не был. То есть
преобразование не запускалось ни разу и Ia_kod был мёртв.

Оба SOC переведены на ADC_TRIGGER_EPWM1_SOCA - он уже работает и стреляет
ровно в такт с обработчиком (тогда это был INT_myEPWM1_ISR; 19.08.2026 такт
переехал на прерывание самого ADCB, см. раздел 2 - но триггер SOCA остался
тем же).

Проверено на цели: до правки Ia_kod и Ib_kod стояли в нуле намертво,
после - оба живые. Значения при этом мусорные, потому что датчиков нет
и входы висят в воздухе: оба гуляют в пределах почти всей шкалы. Это
нормальное поведение неподключённого входа АЦП, а не признак сигнала.

Важное следствие для отладки: пока датчиков нет, модель выключать нельзя.
С выключенной моделью в контур тока пойдёт наводка с плавающих входов.

7.2 КАЛИБРОВКА КАНАЛОВ

Текущие коэффициенты - явные заглушки:

    kadc.Ia = 90   -> 0.009 А/код -> шкала +-18.4 А
                      для вторички 3 кВт (19.3 А пика) впритык,
                      для первички при 48 В (88 А пика) мало вчетверо
    kadc.Vin = 100 -> 0.01 В/код -> шкала 20 В, под АКБ 60 В не годится
    масштаба U220 в kadc нет вообще - заведён отдельный gt.kU220 (было 0.152,
                      с 07.10.2026 0.2 В/код - с запасом над пиком 311 В)
                      (311 В пика на 2048 кодов), тоже требует тарировки

7.3 ОТКРЫТЫЕ ВОПРОСЫ ПО ПЛАТЕ

    - Разводка датчиков тока окончательно не решена. Пока стоят ADCIN1 (Ia)
      и ADCIN7 (Ib), как в текущем syscfg.
    - Судя по комментарию в 1ph_Sin.c, CMPSS1 DACL выведен на пин A1/B7/D11,
      а Ib сидит на ADCB ADCIN7, то есть на B7 - тот же физический пин.
      На стенде датчика нет и это не мешает, но датчик вторички на этот пин
      ставить нельзя. ПРОВЕРИТЬ ПО DATASHEET - замером это не решается:
      оба входа сейчас плавающие и оба ловят наводку во всю шкалу, так что
      отличить просачивание с ЦАП от обычного дрейфа по кодам не выходит.
    - Полярность датчиков: gt.iSign = +1 или -1. Ток должен быть положительным,
      когда течёт ИЗ моста В сеть. Проверяется первым же пуском на малом токе.

9. ПОЧЕМУ УДАЛЁН sine_invertor1
--------------------------------------------------------------------------------
   Решение от 17.08.2026. Касается и автономного режима тоже, не только
   сетевого: трансформатор на выходе стоит в обоих.

Было два метода формирования синусоиды:

    метод 1   в каждой полуволне модулирует ОДНО плечо, второе стоит
              с постоянно открытым нижним ключом
    метод 2   оба плеча модулируются всегда, скважностями duty и (1-duty)

9.1 НА БУМАГЕ ОБА ЧИСТЫ

Доля открытого состояния плеча = 1 - CMPA/TBPRD. Пусть k = gain/2048.

Метод 1, положительная полуволна: dA = k*duty, dB = 0 -> U_AB = k*duty*Udc
        отрицательная:             dB = -k*duty, dA = 0 -> U_AB = k*duty*Udc
Метод 2:  dA = 1-k*duty2, dB = 1-k*(1-duty2), duty2 = 0.5*(1+sin)
          U_AB = k*(1-2*duty2)*Udc = -k*sin*Udc

Оба дают ноль в среднем за период. Идеальная математика их не различает.
Вся разница в том, как каждый превращает несовершенства ЖЕЛЕЗА в постоянную
составляющую.

9.2 КВАНТОВАНИЕ - ЗДЕСЬ ВЫИГРЫВАЛ МЕТОД 1

Присваивание float в uint16_t усекает к нулю.

Метод 1: положительная полуволна смещена на +0.5 кода, отрицательная на -0.5.
Это меандр, среднее ноль. Обе полуволны чуть шире правды, но СИММЕТРИЧНО.

Метод 2 в прежней редакции считал cmpaB вычитанием из уже усечённого cmpaA:
    cmpaB - cmpaA = tbperiod*(2*duty-1) + 2*frac - 0.5,   E[2*frac-0.5] = +0.5
Односторонний сдвиг в полкода: при TBPRD = 7500 это 6.7e-5 от Udc, то есть
3 мВ на первичке и ~22 мВ на вторичке.

ИСПРАВЛЕНО 17.08.2026: оба компаратора считаются независимо из float,
смещения усечений одинаковы и в разности сокращаются.

9.3 АСИММЕТРИЯ ПЛЕЧ - ЗДЕСЬ МЕТОД 1 ПРОВАЛИВАЕТСЯ, И С ОТРЫВОМ

Вот главное, и это структурный порок, а не вопрос настройки.

    положительная полуволна:  модулирует плечо A, держит нижний ключ B
    отрицательная полуволна:  модулирует плечо B, держит нижний ключ A

КАЖДАЯ ПОЛУВОЛНА ФОРМИРУЕТСЯ СВОИМ ЖЕЛЕЗОМ. Всё, чем плечо A отличается
от плеча B, попадает целиком в одну полуволну и не попадает в другую:

    - разброс задержек драйверов затвора (сотни нс - обычное дело)
    - разброс времени выключения ключей
    - падение Vce(sat) на нижнем ключе, держащем ток всю полуволну
    - разная тепловая точка плеч

Любое из этого -> вольт-секунды полуволн не равны -> постоянная составляющая.

Порядок величины: мёртвое время 2 мкс на периоде ШИМ 200 мкс при Udc = 48 В
даёт полную вольт-секундную ошибку 2/200*48 = 0.48 В. Расхождение плеч всего
в 10 % от неё - это 48 мВ на первичке и 336 мВ на вторичке. В ПЯТНАДЦАТЬ РАЗ
больше, чем ошибка квантования метода 2 из 9.2, и 10 % - оценка оптимистичная.

Метод 2 этой болезни лишён по построению: оба плеча коммутируют в обеих
полуволнах, каждый ключ работает и там и там, разброс усредняется, а не
расслаивается по полуволнам.

9.4 ДЛЯ ЗАМКНУТОГО КОНТУРА ТОКА МЕТОД 1 НЕ ГОДИТСЯ ВООБЩЕ

Знак U_AB у метода 1 жёстко привязан к знаку ОПОРНОЙ синусоиды: в положительной
полуволне мост физически не может выдать отрицательное напряжение.

Контуру тока это нужно регулярно - сбить ток около переходов через ноль,
отработать возмущение в другую сторону. Модулятор такую команду не исполнит,
регулятор упрётся в ОДНОСТОРОННЕЕ ограничение. А односторонняя насыщенность -
сама по себе машина по производству постоянной составляющей: одна полуволна
отрабатывается, вторая обрезается.

Именно поэтому grid_tie.c пишет свой модулятор (см. раздел 4), а не
переиспользует ни один из этих двух.

9.5 ЧТО СДЕЛАНО

    - sine_invertor1 удалён, ветка по sine_metod в INT_myEPWM1_ISR убрана
    - sine_invertor2 исправлен: независимый расчёт обоих компараторов (9.2)
      и ПОЛЯРНОСТЬ. В прежней редакции U_AB = -k*sin, то есть переход на этот
      метод развернул бы мост на 180 градусов относительно dacb, к которому
      привязан контур фазы. На стенде это незаметно, на сети - максимальный
      возможный ток. Теперь U_AB = +k*sin, как было у метода 1.
    - убраны DINT/EINT вокруг записи компараторов: оба регистра теневые и
      грузятся одновременно по TBCTR = 0, пара атомарна относительно ШИМ сама
      по себе, а EINT посреди обработчика открывал окно вложенных прерываний
    - команда CAN 622 зажимает sine_metod в 2, чтобы обратное чтение говорило
      правду и метод 1 нельзя было "вернуть" с пульта

Цена решения: переключений вдвое больше, потери на коммутацию выше. Это
осознанная плата за то, что постоянная составляющая перестаёт быть
структурной. Трёхуровневость при этом сохраняется (см. раздел 4), так что
проигрыш по потерям меньше, чем кажется по числу переключений.



10. КОМПАРАТОРЫ, АВАРИЙНЫЕ ЛИНИИ И ПОЛЯРНОСТЬ ДРАЙВЕРОВ
--------------------------------------------------------------------------------
   Раскладка от 17.08.2026, под новую плату (она в разводке).

10.1 ЧТО ЕСТЬ В КРИСТАЛЛЕ

Компараторов четыре: CMPSS1..CMPSS4. У каждого независимые верхний и нижний
компараторы со своими ЦАП: DACH -> CTRIPH, DACL -> CTRIPL.

Аналоговых выходов всего два:
    DACA          настоящий 12-битный ЦАП, пин A0/B15/C15
    CMPSS1.DACL   в режиме внешнего ЦАП, пин A1/B7/D11

Оба 12-битные, шкала 0..4095. Прежняя редакция этого раздела приписывала
CMPSS1.DACL 11 бит - ошибка; драйверлиб проверяет value < 4096, и код всё
это время писал полную шкалу без сдвига, то есть работал правильно.
Комментарий в 1ph_Sin.c про ">> 1" тоже исправлен.

И это ключевое ограничение: в asysctl.h определено ЕДИНСТВЕННОЕ значение
ASYSCTL_CMPSS1_DACL. Наружу выводится нижний ЦАП только модуля CMPSS1,
у CMPSS2/3/4 такой возможности нет. Перенести отладочный вывод нельзя.

10.2 РАСКЛАДКА

    CMPSS1   отладочный вывод через DACL, источник выбирается dacDbgSrc
             (см. 6.1). Компаратор НЕ используется.
    CMPSS2   защита Ia, ток первички.        Вход H=3, L=3 -> A10/B1/C10
    CMPSS3   детектор нуля U220 -> eCAP1.    Вход H=2   -> A0/B15/C15
    CMPSS4   защита Ib, ток вторички.        Вход H=0, L=0 -> B4/C8

Из-за 10.1 Ib нельзя было оставить на CMPSS1: его DACL - это одновременно
и вывод dacb, и отрицательный порог тока. Одно и то же железо.

10.3 ЛОВУШКА: ЧЕТЫРЕ НЕЗАВИСИМЫХ МУЛЬТИПЛЕКСОРА НА ОДИН МОДУЛЬ

Вход каждого CMPSS выбирается ЧЕТЫРЬМЯ раздельными регистрами: CMPHPMXSEL,
CMPHNMXSEL, CMPLPMXSEL, CMPLNMXSEL. Ловушка именно в этом - не в том, что
у них разные списки. Списки у HP и LP как раз ОДИНАКОВЫЕ, индекс в индекс
(TRM табл. 14-1). Прежняя редакция этого раздела утверждала обратное - это
была ошибка, ниже исправленные таблицы.

Опасность в независимости: задашь H и L разные индексы - и две полярности
токовой защиты будут смотреть на РАЗНЫЕ пины. Компилятор промолчит,
SysConfig промолчит, на стенде при однополярной проверке тоже всё выглядит
рабочим. Поэтому для Ia строго H=3 И L=3, для Ib строго H=0 И L=0.

Единственная настоящая асимметрия во всей таблице: у HP есть индекс 7
(термодатчик), у LP индекса 7 нет. К нашей раскладке отношения не имеет.

Отрицательные входы HN/LN - это ОТДЕЛЬНЫЙ, короткий список: всего два
индекса против восьми у положительных. Похоже, именно отсюда и родился миф
про "укороченный список нижнего компаратора". Мы HN/LN не трогаем вообще,
оба компаратора сравнивают вход с внутренним ЦАП.

А "два пина у CMPSS2" в SysConfig - это просто способ записи, не сюрприз:
A10/B1/C10 - один физический вывод, у которого три имени каналов АЦП, и он
же вход 3. B0/C11 - это ВХОД 4, соседняя строка того же списка, отдельный
индекс, доступный обеим полярностям.

Полные таблицы входов для нашего корпуса 100PZ (100 QFP). Одинаковы для H
и L, если не отмечено иное; в скобках - что есть у кристалла, но на этом
корпусе не выведено:

  CMPSS1: 0=A2/B6/C9/PGA1_INP  1=A11/B10/C0/PGA2_OUT  2=A6/D14/E14
          3=(A15 - нет на 100PZ)  4=A1/B7/D11/CMPSS1_DACL (наш dacb)
          5=B5/D15/E15  6=PGA1_OUT_INT
  CMPSS2: 0=A4/B8  1=A12  2=A9  3=A10/B1/C10  4=B0/C11  5=A5
          6=PGA3_OUT_INT  7=TempSensor (только H)
  CMPSS3: 0=B2/C6/E12  1=B12/C2/PGA2_INM  2=A0/B15/C15/DACA_OUT
          3=B3/PGA2_INP  4=A14/B14/C4/PGA1_OUT  5=A3  6=PGA2_OUT_INT
  CMPSS4: 0=B4/C8  1=A7/B30/C3/D12/E30  2=C1/E11/PGA3_INP  3=C14
          4=A8 (B0/C11 - нет на 100PZ)  5=B11/D16/E16

Сноски по корпусу в TRM читать обязательно, они несимметричны: B0/C11 и A5
у CMPSS2 существуют ТОЛЬКО на 100 QFP - нам повезло, у нас он и есть.
A15 у CMPSS1 и B0/C11 у CMPSS4 - ровно наоборот, на 100 QFP их НЕТ. Так что
таблицу выше нельзя молча перенести на плату с другим корпусом.

И проверяйте, что компаратор и АЦП смотрят на ОДИН пин: мультиплексор
компаратора и канал АЦП выбираются независимо, SysConfig об их расхождении
НЕ предупредит - это просто два разных пина, а не конфликт.

10.4 АВАРИЙНЫЕ ЛИНИИ

    TRIP4   аварии драйверов ключей (входы INPUTXBAR). Как было.
    TRIP5   токовая защита от компараторов. Новое, TRIP_Init() в myEPWM.c.

Раздельные линии нужны не для красоты. Обработчик INT_EPWM2_Iu_TZ_ISR по TRIP4
читает сдвиговый регистр, чтобы понять, какой транзистор пожаловался. Заведи
туда же ток - и каждое срабатывание токовой защиты стало бы trip4_uknow.
Теперь причина видна сразу по флагу TZFLG.bit.DCBEVT1, а фаза - по защёлкам
COMPSTS компараторов CMPSS2/CMPSS4.

Мультиплексоры EPWM X-BAR на F28P55x:
    MUX02 = CMPSS2_CTRIPH_OR_L   -> Ia
    MUX06 = CMPSS4_CTRIPH_OR_L   -> Ib
Вариант CTRIPH_OR_L несёт ОБЕ полярности одной линией - для переменного тока
именно то, что нужно.

DCAH у EPWM1/EPWM2 уже занят линией TRIP4, поэтому ток заведён на канал B:
TRIP5 -> DCBH -> DCBEVT1 -> one-shot.

ONE-SHOT ЗДЕСЬ - ВЫБОР, А НЕ ЕДИНСТВЕННЫЙ ВАРИАНТ. У того же DCBEVT1 есть
режим cycle-by-cycle: событие не защёлкивается, а обрывает импульс до конца
периода. Для защиты нужен именно one-shot - превышение тока должно остановить
мост, а не подстричь такт и поехать дальше. Но ровно на cycle-by-cycle строится
пиковое токовое управление, а с ним и самый изящный способ борьбы с постоянкой
в трансформаторе: перекос потока обрывает длинный импульс сам, каждый такт.
Заготовка на будущее разобрана в 3.1.9 - вместе с тем, чего для неё не хватает
и с чем она конфликтует.

10.5 ПОЛЯРНОСТЬ ДРАЙВЕРОВ - ОТКРЫТЫЙ ВОПРОС

Аварийное действие trip-zone зависит от того, каким уровнем закрывается ключ.
Плата в разводке, решение отложено, поэтому полярность вынесена в ОДИН
параметр: IGBT_ACTIVE_HIGH в my_Files/myEPWM.h.

По умолчанию 1 (active-high), потому что этому отвечает всё остальное:
    - мёртвое время EPWM настроено с полярностью по умолчанию (комплементарная
      active-high). При active-low драйверах оно даст ПЕРЕКРЫТИЕ вместо паузы,
      то есть сквозной ток;
    - модулятор: больше duty -> дольше HIGH -> больше выходное напряжение.

Комментарии в pwm_funcs.c ("1 - выключает IGBT") отвечали обратному варианту
и достались от старого проекта. Цена этой несогласованности высокая: при
active-high драйверах прежний IGBT1_Disable() не закрывал бы ключи, а ОТКРЫВАЛ
их - а именно он вызывается по аварии из grid_tie_background(). Теперь обе
функции берут уровень из IGBT_ACTIVE_HIGH.

ЕСЛИ ОКАЖЕТСЯ active-low: поставить IGBT_ACTIVE_HIGH = 0 И ОТДЕЛЬНО сменить
полярность мёртвого времени в SysConfig. Одного параметра не хватит.

11. КОНТУР ВЫХОДНОГО НАПРЯЖЕНИЯ В РЕЖИМЕ АИН
--------------------------------------------------------------------------------
   Сделано 25.09.2026. Где: быстрая половина - grid_tie_apply_uref()
   (grid_tie.c), медленная - Cla1Task1 (CLA/Task1.cla). Хозяйство целиком
   в CLA/cla_shared.h, префикс имён uOut.

До этого дня остров был РАЗОМКНУТЫМ контуром, и это надо назвать своим именем:
амплитуду задавал sineB.gain, посчитанный ОДИН РАЗ по команде оператора из
уставки, коэффициента трансформации и напряжения звена. Дальше он жил
неизменным. Напряжение на выходе от этого падало по двум независимым причинам:

    от нагрузки        падение на сопротивлении обмотки и на индуктивности
                       рассеяния в расчёт не входило вовсе
    от входного        просадка АКБ под током, а с ней и пульсация 100 Гц,
                       которую однофазный мост создаёт сам (3.3)

11.1 ДВА УРОВНЯ И ПОЧЕМУ ИМЕННО ТАК

    каждый такт, CPU   gain = 2048 * (uOutRef + uOutCor) * sqrt2 / (n * Udc)
    раз за окно, CLA   e         = uOutRef - uSec_rms
                       uOutCorI += uOutKi * e
                       uOutCor   = uOutCorI + uOutKp * e,  |uOutCor| < uOutCorMax

Это та же связка, что в сетевом режиме (1.1): прямая связь снимает с регулятора
основную часть работы, а регулятору остаётся остаток. Только там прямой связью
служит измеренное напряжение сети, а здесь - собственная уставка, делённая на
измеренное напряжение звена.

ДЕЛЕНИЕ НА МГНОВЕННОЕ Udc - НЕ ОПТИМИЗАЦИЯ, А ПОЛОВИНА ВСЕЙ РАБОТЫ. Однофазный
мост тянет из АКБ мощность с пульсацией 100 Гц, звено качается с той же
частотой, и прямая связь убирает эту качку из амплитуды выхода В ТОТ ЖЕ ТАКТ.
Медленному ПИ такое недоступно в принципе: его окно - целый период выхода, он
этой пульсации даже не видит. Отсюда и место: прямая связь обязана считаться
каждый такт, значит она на CPU, рядом с формирователем.

Регулятору достаётся то, чего прямая связь про тракт не знает: падения в
трансформаторе, вольт-секундная ошибка мёртвого времени, расхождение gt.n с
настоящим коэффициентом. Всё это МЕДЛЕННОЕ - меняется с нагрузкой, а не внутри
периода, - поэтому окна в период хватает с запасом.

11.2 ПОЧЕМУ ПИ, А НЕ PR, И ПОЧЕМУ ПОПРАВКА В ВОЛЬТАХ ДЕЙСТВУЮЩИХ

Регулируется ДЕЙСТВУЮЩЕЕ значение, то есть уже усреднённая за период величина.
Переменной составляющей на входе регулятора нет, отрабатывать на 50 Гц нечего,
и резонатор был бы ответом на несуществующий вопрос. Контур тока - другое дело,
там сигнал переменный по определению (1.2).

Пропорциональная часть нужна здесь не для затухания, как в контуре подавления
постоянки (3.1.6), а для скорости: объект безынерционный, амплитуда идёт за
gain в тот же такт, и звену "интегратор на интеграторе" взяться неоткуда.

ПОПРАВКА СЧИТАЕТСЯ В ВОЛЬТАХ ДЕЙСТВУЮЩИХ, а не в амплитуде и не в кодах gain.
При таком выборе коэффициент передачи от uOutCor к uSec_rms равен ЕДИНИЦЕ, и
коэффициенты читаются прямо:

    uOutKp = 0.3   снять треть ошибки сразу
    uOutKi = 0.1   добрать десятую часть за период

Переведи поправку в коды - и оба пришлось бы пересчитывать после каждой правки
gt.n или UdcFixed, потому что в кодах коэффициент передачи от них зависит.

ЗАПАЗДЫВАНИЕ ПЕТЛИ около полутора окон: uSec_rms за закрывшееся окно
подставляется в поправку, которая отработает в следующем. При паре 0.3/0.1
установление выходит за 5-10 периодов, то есть 0.1-0.2 с.

11.3 ГДЕ ЖИВЁТ УСТАВКА

Поле gt.UrefRms из структуры gt УБРАНО. Уставка переехала в CpuToCla1MsgRAM под
именем uOutRef - ровно по той же причине, по которой 24.09.2026 туда переехали
kDC и mDCmax (3.1.4): её правят живьём командой 633, и копия на стороне CLA
разошлась бы с оригиналом на первой же правке. CPU своей CpuToCla1MsgRAM читать
не мешает ничто, поэтому потактовая прямая связь берёт уставку оттуда же.

11.4 ДВА РЕГУЛЯТОРА НА ОДИН gain - ЭТОГО НЕ ДОЛЖНО СЛУЧИТЬСЯ

sineB.gain в сетевом режиме ведёт слежение за огибающей U220 (u220_sample в
myADC.c), и там это правильно: перед замыканием контактора мост обязан набрать
именно СЕТЕВОЕ напряжение, а не своё представление о нём.

Поэтому разрешение контуру напряжения - отдельный сигнал uOutAllow, и условий
в нём два:

    gridMode = 0              иначе дрались бы за один и тот же gain
    открытые ключи            иначе uSec_rms лежит в нуле (на модели
                              тождественно, на железе в шумах датчика),
                              и интегратор за секунду уехал бы в потолок,
                              компенсируя напряжение, которого не просили

Пишет его grid_tie_measure(), каждый такт, той же строкой, что и dcAllow, и по
той же причине: одна функция на оба режима, живой сигнал вместо настройки.

ФРОНТ 0 -> 1 СБРАСЫВАЕТ ПОПРАВКУ. Остров обязан начинаться с чистой прямой
связи: поправка, набранная в прошлом заходе, считалась под другую нагрузку и
другое звено, и ушла бы в мост первым же тактом. При смене УСТАВКИ сброса нет
намеренно - интеграл держит падение в трансформаторе, которое от новой уставки
никуда не делось.

11.5 ПОТОЛКИ - ИХ ДВА, И ОНИ ПРО РАЗНОЕ

ПЕРВЫЙ, gt.mMax, стоит на самой амплитуде: gain не может превысить 2048*mMax.
Амплитуда индекса модуляции в острове равна gain/2048 (вывод - в sine_invertor2),
и сверху на неё ложится ещё поправка постоянки mDC в пределах mDCmax. Прежние
2047 означали бы |m| = 1.0 плюс mDC, то есть выход за насыщение компараторов.
Упор считает gt.gainSat - счётчик МОНОТОННЫЙ, диагноз ставится по скорости
роста. Отдельно от gt.satCount: ту обнуляет grid_tie_onGridZero(), а она висит
на захвате нуля сети и в острове не зовётся вовсе.

ВТОРОЙ, uOutCorMax, стоит на поправке и отвечает на вопрос "сколько мы готовы
добавить сверх уставки". 60 В при 220 - это 27 %, с большим запасом над теми
единицами вольт, которые падают в трансформаторе.

Упор второго означает, что УСТАВКА НЕДОСТИЖИМА, и причин ровно три - те же, что
в 3.2: просел АКБ, мал коэффициент трансформации, нагрузка больше расчётной.
Через uOutSatLimit окон подряд в упоре grid_tie_background() пишет в журнал
gt_uOutSat (код 67). БЕЗ ОСТАНОВА - мост при этом работает совершенно исправно,
просто выдаёт меньше запрошенного, и гасить из-за просадки АКБ нагрузку,
которая и так питается, было бы странно. Решение остаётся за оператором.

Обычно оба упора приходят вместе: прямая связь утыкается в gt.mMax раньше, чем
ПИ успевает набрать свой потолок.

11.6 ЧЕМ ЗАМКНУТ КОНТУР - И ГЛАВНАЯ ОГОВОРКА ПРО ЖЕЛЕЗО

Обратная связь - uSec_rms, то есть канал A1 (ADCA SOC3/PPB4), действующее за
окно, считает CLA.

    ПОКА DBG_SIN_DAC = 1, НА ЭТОТ ЖЕ ПИН ИЗНУТРИ ВЫВОДИТ ОТЛАДОЧНЫЙ ЦАП
    CMPSS1, И КАНАЛ МЕРЯЕТ ЕГО, А НЕ ДАТЧИК.

На модели это безразлично: uSec_volt пишет plant_sim_step(), подменяя собой всё
измерение, и контур проверяется полностью. А ПЕРЕД ПЕРВЫМ ПРОГОНОМ С ЖЕЛЕЗОМ
ключ обязан уйти в 0 (bin/config_switch.h), иначе петля замкнётся на собственный
ЦАП: регулятор будет честно держать 220 В на сигнале, который сам же и рисует,
а на выходе моста при этом не будет ничего. Ценой станет вывод на осциллограф
двенадцати отладочных сигналов - его придётся заменить лентой кадра F3 (6.2).

Заодно в 0 освобождается CMPSS1 целиком, а с ним защита по току первички (10.1).

11.7 ЧТО СМОТРЕТЬ

    uSec_rms      действующее на выходе, В - оно и регулируется. В окне

    uOutCorI      интегральная часть отдельно: по ней видно, сколько контур

Ток при этом не вырос, а УПАЛ - с 13.5 до 7.0 А: импеданс нагрузки поднялся
с 16 до 29.8 Ом. Падение на обмотке стало меньше, а напряжение просело сильнее
на 8.6 В. Это не ошибка модели и не регулятор - это векторная геометрия, и её
стоит понимать, потому что на активной нагрузке она усыпляет.

Мост в обоих случаях стоит В УПОРЕ, то есть выдаёт свои 0.95*7*48 = 319 В пика,
225.7 В действующих, и дальше работает делитель между импедансом обмотки
(Rwind + j*w*Lleak = 0.5 + j2.51 Ом) и нагрузкой:

    нагрузка          Zнагр           Zсум            отношение    U
    16 Ом             16              16.5 + j2.51    0.959        216.4
    16 Ом + 80 мГн    16 + j25.1      16.5 + j27.6    0.925        208.9
                      |Z| = 29.8      |Z| = 32.2

Оба расчёта сходятся с измеренным в пределах вольта.

СУТЬ. На АКТИВНОЙ нагрузке падение на индуктивности рассеяния стоит в
КВАДРАТУРЕ к напряжению на нагрузке, и в сумму входит вторым порядком: 34 В
падения дают всего 2.6 В потери. На ИНДУКТИВНОЙ оно становится КОЛЛИНЕАРНЫМ
реактивной части нагрузки и вычитается в полный рост.

Отсюда правило, которое легко забыть: рассеяние трансформатора почти безобидно
на активной нагрузке и вредит напрямую на индуктивной. Проверять запас по
индексу модуляции надо на ИНДУКТИВНОЙ, иначе проверка ничего не значит.

Побочно: cos f вышел 0.54, так что "3 кВт" это уже не 3 кВт - S = 1.47 кВ*А
при P = 788 Вт. Мост при этом греется под полный ток, а полезного отдаёт
четверть. Это уже не про контур, но про выбор ImaxSec помнить стоит.

ГЛАВНЫЙ ВЫВОД, И ОН НЕ ПРО РЕГУЛЯТОР. При 220 В и 3 кВт запаса по индексу
модуляции НЕТ ВОВСЕ, и это видно по числам: для 311 В пика на вторичке при
n = 7 нужно m = 0.926 уже на холостом ходу, а потолок 0.95. На всё про всё
остаётся 2.6 %, то есть около 6 В действующих, - а падения при 3 кВт просят
восьми. Контур делает что может, упирается в потолок и честно сообщает об этом
событием 67.

Лечится это НЕ коэффициентами, а разделом 3.2: коэффициент трансформации
выбирается по минимальному напряжению АКБ под током, с запасом 10-15 %. При
n = 7 и 48 В схема на 220 В при полной нагрузке не выходит в принципе, и до
замкнутого контура этого просто не было видно - напряжение молча проседало.

СКОЛЬКО НУЖНО. Считается от требуемого напряжения МОСТА: чтобы держать 220 В
на нагрузке, мост обязан выдать 220 * |Zсум| / |Zнагр|, а n = Uпика / (mMax*Udc).

    нагрузка          U моста      n при Udc = 48    при просевших 42
    16 Ом             229.5 В      7.12              8.14
    16 Ом + 80 мГн    237.7 В      7.37              8.43

То есть ориентир - n = 8.5, и берётся он по ИНДУКТИВНОЙ нагрузке при
МИНИМАЛЬНОМ напряжении АКБ. Два худших случая, взятые по отдельности, дают
7.4 и 8.1, и ни одна из этих цифр не годится: считать надо оба разом.

ЧЕГО ЭТОТ ЗАМЕР НЕ ПРОВЕРЯЛ: нелинейную нагрузку (выпрямитель с конденсатором).
Действующее значение она держать позволит, а форму испортит, и медленный ПИ по
rms с этим не сделает ничего - для формы нужен мгновенный контур напряжения.
Заводить его имеет смысл только после того, как решится вопрос с запасом по m:
сейчас ему просто нечем работать.
