# CAN Bootloader Protocol (F280039C)

Документ описывает фактический протокол обмена между PC-программатором и CAN bootloader на MCU.

## 1. Участники и роли

- **PC (WinForms, `Stepulyov/ASt_MainF.cs`)**
  - отправляет команды и данные прошивки
  - ждёт ACK/статусы от MCU
- **MCU bootloader (`3ph_Inverter/Bootloader/can_bootloader.c`)**
  - принимает команды
  - стирает FLASH
  - программирует блоки
  - проверяет checksum
  - передаёт управление приложению

## 2. CAN IDs и формат кадров

См. `can_boot_protocol.h`:

- **MCU -> PC**: `BOOT_CAN_TX_ID = 0x32`
- **PC -> MCU**: `BOOT_CAN_RX_ID = 0x33`

Кадры — standard 11-bit ID, DLC=8.

Практически команды/ответы кодируются как 16-битное слово в `DATA[0..1]` (little-endian), остальные байты обычно 0.
* little-endian — это порядок байт, где младший байт идёт первым.
Исключение: заголовок загрузки после `CMD_LOAD` передаётся одним 8-байтным кадром (4 слова подряд).
 

- Отправка слова из PC: `Send_33(ushort)`
- Приём слова на PC: `Read_32()`
- Отправка слова из MCU: `boot_can_send_word(uint16_t)`
- Приём слова на MCU: `boot_can_recv_word()` / `boot_can_recv_word_blocking()`

## 3. Последовательность фаз (state machine)

## 3.1 Handshake

1. PC шлёт `CMD_HANDSHAKE (0xCC01)` циклически.
2. MCU в цикле ждёт это слово.
3. MCU отвечает `ACK_HANDSHAKE (0x02CC)`.

Только после этого переход к erase.

## 3.2 Erase

1. PC шлёт `CMD_ERASE (0xCC02)`.
2. PC сразу шлёт 8-байтный кадр диапазона стирания:
   - `startHi`, `startLo`, `endHi`, `endLo` (inclusive, word addresses)
   - MCU стирает только сектора, пересекающиеся с этим диапазоном.
   - Если кадр диапазона не пришёл/повреждён, MCU не делает fallback на полный диапазон, а переходит в error/recovery flow.
3. MCU шлёт `ACK_ERASE_RANGE (0x0DCC)` только после успешного приёма/валидации кадра диапазона.
4. MCU начинает стирание банков/секторов приложения.
5. MCU шлёт статусы прогресса (ID `0x32`):
   - `0xEE01`, `0xEE00`, `0xEE02` — диагностические маркеры
   - `0xEB0s` — Bank0 sector `s`
   - `0xEB1s` — Bank1 sector `s`
   - `0xEB2s` — Bank2 sector `s`
6. При ошибках таймаута FSM MCU шлёт: `0xD0nn/0xD1nn/0xD2nn`.

   Где **FSM** = **Flash State Machine** (внутренний автомат контроллера FLASH),
   который выполняет операции стирания/программирования и сигнализирует готовность.

   Подробно по формату:

   - `0xD0nn` -> timeout при стирании сектора в **Bank0**
   - `0xD1nn` -> timeout при стирании сектора в **Bank1**
   - `0xD2nn` -> timeout при стирании сектора в **Bank2**

   Где:

   - старший байт (`0xD0/0xD1/0xD2`) кодирует номер банка
   - младший байт `nn` кодирует индекс сектора, на котором зафиксирован timeout ожидания готовности FSM

   Источник в коде MCU:

   - маркер формируется в `boot_wait_fsm_ready(timeoutWord)`
   - в `bootloader_erase_app_flash()` в функцию передаётся:
     - Bank0: `0xD000 | sector`
     - Bank1: `0xD100 | sector`
     - Bank2: `0xD200 | sector`

   Примеры:

   - `0xD00A` -> timeout FSM на Bank0, Sector10
   - `0xD105` -> timeout FSM на Bank1, Sector5
   - `0xD20F` -> timeout FSM на Bank2, Sector15

   Что это означает по сути:

   - команда `Fapi_issueAsyncCommandWithAddress(Fapi_EraseSector, ...)` была принята,
   - но `Fapi_checkFsmForReady()` не вернул готовность в отведённое окно ожидания,
   - bootloader сообщает конкретный банк/сектор и завершает фазу erase с ошибкой;
   - далее MCU остаётся в RAM в режиме recovery и ждёт решение от PC (без автоматического reset и без fallback).

   > Примечание (простыми словами):
   >
   > - **FSM** — это аппаратный блок внутри MCU (**Flash State Machine**), который реально стирает/программирует FLASH.
   > - **FAPI** — это программная библиотека/интерфейс, через который код управляет этим аппаратным FSM.
   > - Поэтому длинные функции `Fapi_*` — это не "сам FSM", а команды/проверки для работы с ним.

   Рекомендуемая обработка на PC:

   - немедленно прекращать цикл erase,
   - показывать диагностическое сообщение с bank/sector,
   - не переходить к `CMD_LOAD`.
7. После успешного erase MCU шлёт `ACK_ERASE (0x05CC)`.

PC в это время в цикле читает статусы прогресса `Read_32()` до `0x05CC`, показывая прогресс erase.

## 3.3 Load header (переход к загрузке)

1. После получения `ACK_ERASE` PC отправляет `CMD_LOAD (0xCC07)` для первого сегмента.
2. MCU отвечает `ACK_LOAD_READY (0x0ACC)`.
3. Только после `ACK_LOAD_READY` PC отправляет кадр header (8 байт): `addrHi`, `addrLo`, `sizeHi`, `sizeLo`.
4. MCU принимает header и переходит в data-phase для этого сегмента.

   Практическое правило для PC:

   - header отправляется только после ACK на `CMD_LOAD`;
   - допустимые ACK в PC-программаторе: `ACK_LOAD_READY (0x0ACC)` и `ACK_LOAD (0x07CC)` для совместимости между версиями;
   - фиксированные задержки между `CMD_LOAD` и header не требуются.

   Наблюдаемый симптом при слишком плотной отправке без паузы:

   - MCU продолжает слать `ACK_ERASE (0x05CC)` и не переходит в data-phase.

   Формат кадра 2 (`DLC=8`, little-endian слова):

   - bytes `[0..1]` -> `addrHi`
   - bytes `[2..3]` -> `addrLo`
   - bytes `[4..5]` -> `sizeHi`
   - bytes `[6..7]` -> `sizeLo`

Важно: это самая чувствительная точка протокола.

## 3.4 Передача данных (program)

Термины в этой фазе:

- **Сегмент** — один непрерывный payload-участок прошивки, объявленный в header после `CMD_LOAD` (`addrHi/addrLo + sizeHi/sizeLo`).
- **data-блок сегмента** — один CAN-кадр данных `DLC=8` (8 байт), то есть одна порция данных внутри текущего сегмента.

1. После ACK на `CMD_LOAD` PC отправляет header сегмента (`addrHi/addrLo/sizeHi/sizeLo`).
2. PC сразу начинает отправку данных сегмента блоками по 8 байт (DLC=8, ID=0x33).
3. MCU на каждый блок сегмента:
   - принимает 8 байт
   - программирует FLASH (64 бита)
   - шлёт `ACK_BLOCK (0x06CC)`
4. PC после каждого отправленного блока ждёт `0x06CC`.
5. После завершения сегмента MCU шлёт `ACK_LOAD (0x07CC)`.
6. Далее PC:
   - либо отправляет следующий `CMD_LOAD` (следующий сегмент),
   - либо отправляет `CMD_VERIFY` (если сегменты закончились).

Пример:

- если `segment = 26` байт, это 4 data-блока: `8 + 8 + 8 + 2`;
- последний кадр физически всё равно передаётся как `DLC=8`, но логически полезны только последние 2 байта сегмента.

Примечание: PC отправляет не сплошной образ, а только «payload» сегменты (без промежутков из `0xFF`).

### 3.4.1 Обновление протокола PC-программатора (апрель 2026)

- Убрано ожидание «предварительного первого `ACK_BLOCK`» до отправки data-блока.
- Передача стала строго подтверждаемой по схеме «отправил блок -> получил `ACK_BLOCK`».
- Для `CMD_LOAD` добавлена совместимость по ACK: принимаются `0x0ACC` и `0x07CC`.
- Это убирает зависимость от скорости конкретного ПК/драйвера и предотвращает зависание на `Загрузка...0%`.

Коды ошибок программирования:

- `0xDFxx` — код статуса Fapi
- `0xDEAD` — фатальная ошибка

Где это наблюдается:

- эти слова приходят от MCU в кадрах с `ID=0x32` во время фазы program (вместо ожидаемого `ACK_BLOCK`/`ACK_LOAD`);
- обычно видны в CAN trace, в `Bootloader_trace.log` и в UI-логе/статусе программатора как ответ bootloader.

Что с ними делать на PC:

- немедленно прервать текущую сессию загрузки (не переходить к следующему сегменту и не отправлять `CMD_VERIFY`);
- показать пользователю диагностику:
  - для `0xDFxx` — вывести `xx` как код ошибки Fapi;
  - для `0xDEAD` — вывести сообщение о фатальной ошибке программирования;
- зафиксировать событие в логах;
- предложить пользователю действия recovery: "Повторить с начала" или "Выбрать другой файл";
- при выборе варианта запускать новый цикл с `CMD_ERASE`.

## 3.5 Завершение загрузки и verify

1. После последнего сегмента PC шлёт `CMD_VERIFY (0xCC08)`.
3. MCU отвечает `ACK_VERIFY_READY (0x09CC)`.
4. PC шлёт checksum (2 слова).
5. MCU сравнивает и шлёт:
   - `ACK_VERIFY (0x08CC)` при успехе
   - `ACK_NOVERIFY (0x0ECC)` при несовпадении контрольной суммы
     (в этом случае PC показывает пользователю диалог с тремя вариантами действий — подробнее ниже).

Важно: checksum считается по реально переданным байтам сегментов (без пропусков `0xFF`).

## 3.6 Reboot / jump

1. PC шлёт `CMD_REBOOT (0xFE17)`.
2. MCU шлёт `ACK_REBOOT_READY (0x17FE)`.
3. PC шлёт `entryHi/entryLo`.
4. MCU шлёт `ACK_REBOOT (0x18FE)`.
5. MCU делает `boot_jump_to_app(entryAddr)`.

## 3.7 FAPI-функции простыми словами

Ниже краткая «шпаргалка» по основным вызовам `Fapi_*`, используемым в загрузчике:

- `Fapi_initializeAPI(...)`
  - «Включи библиотеку Flash API и подготовь её к работе».
- `Fapi_setActiveFlashBank(bank)`
  - «Выбери, с каким банком FLASH сейчас работаем (Bank0/1/2)».
- `Fapi_setupBankSectorEnable()`
  - «Разреши операции по секторам выбранного банка».
- `Fapi_issueAsyncCommandWithAddress(Fapi_EraseSector, addr)`
  - «Запусти стирание сектора по адресу `addr`».
- `Fapi_checkFsmForReady()`
  - «Проверь, закончил ли аппаратный FLASH-движок (FSM) операцию».
- `Fapi_getFsmStatus()`
  - «Получи итог: успех или код ошибки после операции».
- `Fapi_issueProgrammingCommand(addr, data, ...)`
  - «Запиши данные во FLASH по адресу `addr`».

## 3.8 Ошибки erase/program

Для ошибок erase/program MCU отправляет диагностический код (`0xD0nn/0xD1nn/0xD2nn`, `0xDFxx` или `0xDEAD`),
после чего не делает принудительный reset, а переходит в recovery-ожидание команды от PC.

Рекомендуемый recovery-flow:

- PC по коду ошибки открывает пользователю окно проблемы;
- варианты действий:
  1) "Повторить с начала" — PC очищает очередь ответов и отправляет `CMD_ERASE` (новая сессия erase/load/verify);
  2) "Выбрать другой файл" — PC выбирает/конвертирует новый файл и затем также начинает с `CMD_ERASE`.

Ключевое правило: при ошибке MCU остаётся в RAM и не уходит в fallback/reset до явной команды от PC.

## 4. Ограничения FLASH и errata

В `bootloader_program_block()`:

- Для F280039C учтена errata: последние 16 слов Bank2 (`0x0AFFF0..0x0AFFFF`) **не программируются**.
- Эти байты остаются `0xFF`, при этом checksum на PC/MCU считается согласованно.

Область приложения:

- start: `0x082000` (Bank0 Sec2)
- end: `0x0AFFFF`

Область bootloader (Sec0-1) не стирается и не программируется.

## 4.1 Дополнения по поведению PC (актуально для реальной реализации)

- Текущий рабочий режим передачи: `per-block ACK` (`ACK_BLOCK` после каждого 8-байтного блока).
- Для удаления тайминговой зависимости используются явные ACK-этапы:
  - `CMD_ERASE` -> `ACK_ERASE_RANGE`,
  - `CMD_LOAD` -> `ACK_LOAD_READY`.
- Загрузка выполняется сегментами: PC отправляет только непустые участки (без `0xFF` gap),
  каждый сегмент — отдельный `CMD_LOAD + header + data`.

- При несовпадении контрольной суммы MCU возвращает `ACK_NOVERIFY (0x0ECC)` и PC должен показать диалог
  с тремя опциями (локальная терминология):
  0) "Повторить" — быстрый retry: не переинициализировать CAN, очистить очередь ответов и перейти к `CMD_ERASE`;
  1) "Выбрать другой .out" — позволить выбрать новый файл, переконвертировать и перезапустить erase/load;
  2) "Прервать (без ребута)" — отменить сессию без перезапуска MCU.

- PC создаёт лог-файлы для последующего анализа:
  - `Bootloader_trace.log` — хронология ключевых событий/ответов во время сессии (handshake/erase/load/verify).
  - `Bootloader_perf.log` — измерения производительности: время стирания/загрузки/верификации, средние RTT/throughput.
  - `Bootloader_error.log` — ошибки конвертации/исключения, возникающие при подготовке .out/.bin (если есть);
  - временные/вспомогательные файлы, создаваемые во время сессии:
    - `Ldr.out`, `Ldr.bin` — рабочие копии/сконвертированные файлы прошивки;
    - файлы `*.b00`, `*.bin`, `*.out` — временные артефакты (функция `Cl()` очищает их после сессии).

  Примечание: по умолчанию все перечисленные файлы создаются в каталоге запуска приложения (`Application.StartupPath`).

- PC использует UI-таймеры и bounded timeouts для ожиданий `ACK_VERIFY_READY` и результата верификации
  (по умолчанию 10 s), чтобы избежать бессрочных зависаний; при таймауте надо логировать и сообщать пользователю.

## 4.2 Разбор ELF entry (`_c_int00`) и fail-fast

Для `ELF` (`.out`) точка входа приложения на MCU должна быть **реальным адресом `_c_int00`**.

Правило извлечения entry на PC:

1. Предпочтительно найти символ `_c_int00` в symbol table ELF.
2. Если символ не найден, допускается декодирование `LB` из `codestart` (по `e_entry`) для получения target-адреса.
3. Если корректный адрес `_c_int00` получить не удалось — **fail-fast**:
   - сессию загрузки прервать,
   - показать пользователю диалог `Неправильный файл`,
   - предложить действия: выбрать другой файл или выйти из режима программатора.

Важно:

- Нельзя использовать молчаливые fallback-адреса (например, `FStartAddr`) как entry.
- `e_entry` сам по себе может указывать на `codestart` (stub), а не на фактический `_c_int00`.
- Переход к `CMD_ERASE/CMD_LOAD` при невалидном entry запрещён.

- Рекомендуемая обработка ошибок на PC:
  - при `0xDFxx`/`0xDEAD` — показать подробную ошибку и предложить: "Повторить с начала" / "Выбрать другой файл";
  - при `0xD0nn/D1nn/D2nn` — показать bank/sector и предложить те же действия;
  - при выборе любого из двух вариантов запускать новый цикл с `CMD_ERASE`.

## 5. Тайминги и таймауты

Ключевые ожидания на MCU реализованы через `boot_delay_stub(100)` в цикле.

Назначение таймаутов на MCU:

- не допустить вечного зависания при потере CAN-кадров или аппаратной ошибке FLASH,
- завершить ошибочную сессию предсказуемо,
- перейти в recovery-состояние и ждать явной команды от PC.

Ключевые ожидания на PC:

- handshake loop
- erase loop
- waiting `0x06CC` at 0%
- per-block ACK wait
- verify/reboot ACK wait

Любые лишние задержки на PC в `Read_32()` (например ожидание события при неактивном receive worker) приводят к рассинхронизации фаз.

## 6. Где обычно зависает и что это значит

## 6.1 UI: `Загрузка...0%`

PC уже отправил `CMD_LOAD + header` и ждёт первый `ACK_BLOCK (0x06CC)`.

Причины:

- MCU не получил `CMD_LOAD` (застрял в фазе ожидания команды загрузки)
- MCU получил `CMD_LOAD`, но не получил первый data-блок
- потеря/гонка кадров на PC между фоновым `_crw` и worker загрузчика

## 6.2 Стек MCU в `bootloader_main` около цикла ожидания `CMD_LOAD`

- это фаза 3 (между erase и program)
- `debug_byteCount == 0` ожидаемо
- означает, что до data-фазы MCU не дошёл

## 6.3 Стек MCU в первом ожидании data-блока (first block wait)

- `CMD_LOAD` уже принят
- заголовок принят
- MCU ждёт первый data CAN кадр

## 7. Наблюдаемые инварианты (для диагностики)

При нормальной сессии порядок ответов MCU (сокращённо):

1. `0x02CC`
2. `... erase markers ...`
3. `0x05CC`
4. `0x06CC` (готов к первому блоку)
5. `0x06CC` на каждый блок
6. `0x07CC`
7. `0x09CC`
8. `0x08CC`
9. `0x17FE`
10. `0x18FE`

Если порядок ломается — проблема транспорт/синхронизация, а не формат бинарника.

## 8. Правила для реализации PC-части (чтобы не ломать протокол)

1. На время прошивки должен быть **один владелец чтения CAN**.
2. Нельзя иметь 300ms задержку на каждый `Read_32()` в фазах erase/load/program.
3. После завершения прошивки нужно корректно освободить bootloader handle и заново подключить UI-канал.
4. Все команды bootloader отправлять с ID `0x33`, DLC=8.
5. Все ответы ждать по ID `0x32`.

## 9. Коды команд/ACK (краткая таблица)

- `CMD_HANDSHAKE = 0xCC01`
- `ACK_HANDSHAKE = 0x02CC`
- `CMD_ERASE = 0xCC02`
- `CMD_ERROR_RECEIVED = 0xCC0E`
- `ACK_ERASE = 0x05CC`
- `CMD_LOAD = 0xCC07`
- `ACK_BLOCK = 0x06CC`
- `ACK_LOAD = 0x07CC`
- `CMD_VERIFY = 0xCC08`
- `ACK_VERIFY_READY = 0x09CC`
- `ACK_VERIFY = 0x08CC`
- `CMD_REBOOT = 0xFE17`
- `ACK_REBOOT_READY = 0x17FE`
- `ACK_REBOOT = 0x18FE`

## 10. Мини-чеклист при регрессии "второй Update CCS"

1. Убедиться, что `_crw` не конкурирует с `FlWrk_DoWork` за чтение CAN.
2. Проверить, что `Read_32()` не ждёт событие, когда `_crw` остановлен.
3. Проверить, что после прошивки PC делает clean reinit USB-CAN для UI.
4. Снять CAN trace ID `0x32/0x33` и сравнить с expected sequence из раздела 7.
5. Проверить MCU стек:
   - в ожидании `CMD_LOAD` или
   - в ожидании первого блока данных.
