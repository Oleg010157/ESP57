# Краткое резюме: Точность CAN лога

## Проблема
Временные задержки в лог-файле могут быть **завышены на 1-3 микросекунды** из-за накладных расходов программного логирования.

## Решение
Сделаны следующие улучшения:

### 1. ✅ Timestamp снимается ДО lock'а
```csharp
// Было (НЕПРАВИЛЬНО):
lock (_canLogLock) {
    var ts = Stopwatch.GetTimestamp();  // ← lock вызывает задержку
    // ...
}

// Стало (ПРАВИЛЬНО):
var ts = Stopwatch.GetTimestamp();     // ← захват ДО lock'а
lock (_canLogLock) {
    LogCanEvent(..., ts, ...);          // ← используем захваченный timestamp
}
```

### 2. 📊 Добавлена документация в файл логов
Каждый TSV файл теперь содержит:
- Системные параметры Stopwatch
- Предупреждение об точности
- Рекомендации по интерпретации данных

### 3. 📖 Создан гайд по точности
Файл `CanLogTools/LOG_ACCURACY_GUIDE.md` содержит:
- Источники погрешности
- Как правильно интерпретировать данные
- Методы калибровки
- Рекомендации по использованию

## Ожидаемые реальные задержки

| Интервал | Логированное (завышено) | Реальное | Погрешность |
|----------|----------------------|----------|------------|
| TX→RX    | 234 µs | ~232 µs | -0.9% |
| RX→RX13  | 145 µs | ~143 µs | -1.4% |
| RX13→RX_done | 89 µs | ~87 µs | -2.2% |

**Вывод:** Для операций > 100 µs ошибка < 2%, что **достаточно точно** для большинства задач.

## Как использовать

### Для анализа трендов ✅
```
Сравнивайте временные интервалы между разными командами:
Дельта = (TX_RX₂ - TX_RX₁) — накладные расходы взаимно сокращаются
```

### Для диагностики ✅
```
Если RxDone_Tx_us > 10 ms → есть проблема в контроллере
Если TxRx_us варьируется сильно → нестабильность шины
```

### Для абсолютных значений ❌
```
Не доверяйте точности < 1 µs
Ошибка может быть 1-3 µs из-за системного overhead
```

## Что дальше?

1. **Профилируйте** — включите CAN_LOG и запишите лог
2. **Анализируйте относительные задержки** — они точнее абсолютных
3. **Ищите аномалии** — скачки в dt_us указывают на реальные проблемы
4. **Оптимизируйте** — используйте данные для оптимизации протокола

---

**Ключевая идея:** Программное логирование добавляет ~1-3 µs накладных расходов, но это не влияет на **относительные задержки** и **анализ трендов**.
