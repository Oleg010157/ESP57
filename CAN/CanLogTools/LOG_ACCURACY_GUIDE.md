# CAN Log Accuracy Guide

## ⚠️ ВАЖНО: О точности временных задержек

### Введение
CAN логирование измеряет временные интервалы между программными событиями (отправка команды и получение ответа). Это **НЕ** прямое измерение задержек на CAN шине.

---

## Источники погрешности

### 1. **Накладные расходы логирования** (~0.5-2 µs на событие)
- Захват timestamp (`Stopwatch.GetTimestamp()`) 
- Блокировка на `_canLogLock` 
- Добавление записи в `List<LogEntry>`
- Контекстное переключение потоков

**Результат:** Задержки завышены примерно на 1-3 µs

### 2. **Время снятия timestamp**
- Timestamp снимается в момент вызова `AppendUiCanLogLine()`, а не в момент фактического события
- Между фактическим событием (TX на шине) и регистрацией может пройти ~100-500 ns

### 3. **Очередь обработки событий**
- RX события обрабатываются асинхронно
- Может быть задержка между получением данных и обработкой

---

## Как интерпретировать результаты

### ✅ Правильное использование данных
- **Относительные задержки** — сравнение между разными командами (ВАЛИДНО)
- **Тренды** — увеличение/уменьшение задержек во времени (ВАЛИДНО)
- **Соотношения** — какая часть времени на TX→RX vs RX→RX13 (ВАЛИДНО)

### ❌ Неправильное использование данных
- **Абсолютные значения** — точные задержки на шине (НЕДОСТАТОЧНО ТОЧНО)
- **Сравнение с теоретическими значениями** — CAN может быть быстрее (МОЖЕТ НЕ СОВПАДАТЬ)
- **Диагностика проблем на шине** — может быть программная задержка (ПРОВЕРИТЬ КОНТЕКСТ)

---

## Калибровка точности

Для оценки накладных расходов можно выполнить калибровку:

### Метод 1: Быстрые команды
1. Отправьте серию быстрых команд без задержек
2. Посмотрите на `dt_us` (разница между событиями)
3. Минимальные значения `dt_us` ~ накладные расходы системы

**Ожидаемые значения dt_us для быстрых событий:**
- TX→RX: 150-300 µs (в зависимости от скорости CAN)
- RX→RX13: 50-200 µs
- RX13→RX_done: 20-100 µs

### Метод 2: Контрольный тест
```
1. Включить логирование
2. Отправить известную команду
3. Посмотреть полное время TX→RX_done
4. Вычесть теоретическое время на CAN шине
5. Разница ~ накладные расходы программы
```

## Рекомендации

### Для точного анализа:
1. **Логируйте длительные операции** — ошибка на 2-3 µs не важна для операций > 1 ms
2. **Используйте относительные задержки** — (TX₂_RX - TX₁_RX) даст разницу без накладных расходов
3. **Игнорируйте первые несколько событий** — могут быть артефакты кэша
4. **Проверяйте тренды** — монотонное увеличение указывает на реальную проблему

### Для диагностики проблем:
- Если `RxDone_Tx_us` > 10 ms → проблема на CAN шине или контроллер "не откликается"
- Если `TxRx_us` > 5 ms → слишком долгая обработка TX буфера
- Если `Rx13_Rx_us` сильно варьируется → нестабильность или перегрузка шины

---

## Формулы расчёта реальных задержек

Если вы хотите **оценить реальные задержки на CAN шине**:

```
Реальная_TX_RX = Логированная_TX_RX - Накладные_Расходы
Накладные_Расходы ≈ 1-3 µs (в зависимости от нагрузки)
```

Но для практики:
- Логированные значения достаточны для оптимизации
- Ошибка в 1-3% для задержек > 100 µs не критична

---

## Параметры Stopwatch

В файле логов указаны:
- `Stopwatch.Frequency` — тактовая частота счётчика
- Разрешение = 1,000,000 µs / Frequency

Для примера:
- Frequency = 10,000,000 → разрешение = 0.1 µs (очень хорошо)
- Frequency = 1,000,000 → разрешение = 1 µs (нормально)

## Выводы

✅ **Используйте логирование для:**
- Анализа относительных задержек
- Выявления аномалий
- Оптимизации протокола CAN
- Отладки последовательности команд

❌ **Не используйте для:**
- Точного измерения задержек шины
- Сравнения с другими системами
- Критичных требований к синхронизации
