# ESP32_BRIDGE — мост SPI ↔ WiFi для прибора K57

ESP32 — ведомый SPI у F28P55x и прозрачный мост в сеть. Провода, режим SPI и
почему так — `docs/esp32-spi-wiring-RU.md`.

Прибор раз в 2 мс отдаёт посылку 512 байт с теми же кадрами, что идут по
CAN FD. Мост отдаёт их в сеть: телеметрию 103 и 140 — по UDP 5521, ACK и
ошибки 132 — по TCP 5520, а команды с TCP — прибору. Формат —
`docs/esp32-spi-protocol-RU.md`, раздел «Сеть», и `main/net_proto.h`; сторона
прибора — `INVERTOR_CCS/my_Files/wifi_link.c` (итоги в Watch: `wifiLink`).

## Сеть

Два режима, выбираются в `sdkconfig.local` (в git не попадает, при первой
сборке создаётся пустым):

- **Только своя точка** — `CONFIG_K57_AP_ONLY=y`. Мост сразу раздаёт сеть
  **`K57`**, пароль `k57bridge`, адрес **192.168.4.1**. Компьютер, телефон или
  планшет подключаются к ней напрямую, роутер не нужен. На стенде это
  надёжнее: через роутер при слабом сигнале эфир не тянул ленту.
- **Общая сеть** — `CONFIG_K57_AP_ONLY=n` и `CONFIG_K57_WIFI_SSID`,
  `CONFIG_K57_WIFI_PASS`. Не подключился за 8 попыток — та же точка `K57`.

Поменяли режим — `idf.py reconfigure`, потом `build`: без него новая
настройка в `sdkconfig` может не попасть (так и вышло 10.11.2026).

В Motor_Control: «Управление → Связь через WiFi (мост K57)». Адрес моста — в
`bin\Debug\link.ini`; не ответил по нему — программа сама пробует 192.168.4.1.
В заголовке окна — имя сети и адрес.

Проверить мост без Motor_Control:

```
python tools/net_test.py                 своя точка K57
python tools/net_test.py 192.168.1.50    мост в общей сети
```

## Консоль

Раз в секунду мост печатает в свой COM-порт (115200), сколько кадров каждого
номера пришло с прибора и что ушло в сеть. Команду прибору можно дать прямо из
монитора: `c <cmd> [d1] [d2] [d3]`, например `c 333` — прибор пришлёт строку с
версией прошивки. Ответы ACK печатаются там же.

## Чёрный ящик

Мост держит в памяти последние ~0,75 с быстрой ленты прибора и по аварии
сохраняет их во флеш — четыре последние записи. В Motor_Control: «Измерения →
Чёрный ящик (WiFi-мост)…», запись сохраняется в .spl для Wscope. Пуск вручную
из консоли моста — `b`. Подробно — `docs/esp32-spi-protocol-RU.md`, «Чёрный
ящик».

Таблица разделов своя (`partitions.csv`, с 10.11.2026). Плату со старой
прошивкой надо прошить целиком (`idf.py flash` так и делает); без раздела
`bbox` мост работает, но чёрный ящик выключен — так и пишет в лог.

## Страница в браузере

С 12.11.2026 мост показывает прибор в браузере: сеть K57, адрес
**http://192.168.4.1** — с компьютера, телефона или планшета, без Motor_Control.
Страница — `main/page/index.html`, вшита в прошивку; данные — запросами
`/api/state`, `/api/errors`, `/api/journal`, `/api/bbox`, `/api/bridge`
(`main/web_page.c`). Описания кодов — вшитый при сборке `bin/ErrorCodes.h`.

- **Прибор** — величины из кадра 140 раз в 0,7 с, в шапке — состояние инвертора
  («стоит, ключи закрыты», «в сети», «АВАРИЯ — …») и круг: красный — есть
  текущая ошибка.
- **Ошибки**, **Журнал** (длинный журнал моста), **Чёрный ящик** (список;
  смотреть записи — в Motor_Control), **Мост** (версия, связь, обновление прошивки).

**Чей сеанс.** Сеанс Motor_Control открыт («Подключить») — страница только
показывает то, что идёт по нему. Сеанса нет (Motor_Control закрыт или в нём
«Отключить») — мост, пока страница открыта, раз в секунду шлёт прибору
команду **344 «только смотреть»**: кадр 140, лампа, список ошибок. Ключи и
уставки она не трогает — работающий инвертор от открытой страницы не встанет.
Сеанс мост узнаёт у самого прибора: бит 0 слова 2 кадра 140 (`sbit.connect`).

Управление со страницы — следующий шаг; при открытом сеансе Motor_Control оно
будет выключено.

Для проверки страницы без настоящей неисправности: в Watch прибора
`dbgNvRaise = <код>` — поднять аварию один раз, `dbgErrBlink = <код>` — мигать
ею (3 с горит, 3 с нет; `dbgErrBlinkSec`), `0` — стоп.

## Сборка и прошивка

ESP-IDF v5.4. В PowerShell окружение поднимается скриптом установщика —
`export.ps1` из самого IDF без системного Python не работает:

```
. C:\Espressif\Initialize-Idf.ps1
cd ESP32_BRIDGE
idf.py build
idf.py -p COM<N> flash monitor
```

### По WiFi, без кабеля

С 12.11.2026 мост обновляется по сети. В Motor_Control: «Управление →
Обновить прошивку WiFi-моста…», файл — `build\esp32_bridge.bin`. Или из
командной строки:

```
curl -u k57:<пароль> --data-binary @build/esp32_bridge.bin http://192.168.4.1/update
```

Пароль — `CONFIG_K57_ADMIN_PASS` в `sdkconfig.local`; не задан — пароль сети
K57. Версия моста — `http://192.168.4.1/version`.

Новая прошивка пишется во второе место под программу и сначала считается
**пробной**: проработала 20 с — подтверждена; не подтвердилась за минуту
(зависла, не завела сеть) — мост перезапускается и возвращается к прежней.
Проверено на стенде: 889 кБ за 9 с; мусорный файл не принят
(`ESP_ERR_OTA_VALIDATE_FAILED`); прошивка без подтверждения через минуту
откатилась сама.

**Возврат к прежней — свойство загрузчика**, а загрузчик по WiFi не
обновляется. Плату со старым загрузчиком (до 12.11.2026) надо один раз прошить
по USB, `idf.py flash`.

### В VS Code

Нужно расширение Espressif IDF. Открывать **папку `ESP32_BRIDGE`**, а не весь
ESP57: расширение ищет `CMakeLists.txt` проекта в корне окна. Сборка, прошивка
и монитор — кнопками в нижней строке. Настройки `.vscode` (версия IDF, порт,
IntelliSense) локальные и в репозиторий не попадают. Подсказки по коду
появятся после первой сборки: пути берутся из `build/compile_commands.json`.

На этой же плате жила прошивка ESP_INV (`C:\Work\ESP_INV\firmware`).
Вернуть её — `idf.py -p COM<N> flash` из её каталога.
