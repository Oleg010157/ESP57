# ESP32_BRIDGE — мост SPI ↔ WiFi для прибора K57

ESP32 — ведомый SPI у F28P55x и прозрачный мост в сеть. Провода, режим SPI и
почему так — `docs/esp32-spi-wiring-RU.md`.

Прибор раз в 2 мс отдаёт посылку 512 байт с теми же кадрами, что идут по
CAN FD. Мост отдаёт их в сеть: телеметрию 103 и 140 — по UDP 5521, ACK и
ошибки 132 — по TCP 5520, а команды с TCP — прибору. Формат —
`docs/esp32-spi-protocol-RU.md`, раздел «Сеть», и `main/net_proto.h`; сторона
прибора — `INVERTOR_CCS/my_Files/wifi_link.c` (итоги в Watch: `wifiLink`).

## Сеть

С 13.11.2026 мост держит две сети сразу:

- **Своя точка `K57`** — всегда. Пароль `k57bridge`, адрес **192.168.4.1**.
  Компьютер, телефон или планшет подключаются к ней напрямую, роутер не нужен.
- **Роутеры** — вдобавок, до четырёх (дом, работа...): вкладка «Мост» на
  странице, «Найти сети», пароль, «Запомнить и подключить». Пароль каждого
  вводится один раз и хранится в NVS моста, не в прошивке и не в git.
  Включившись, мост сам входит в тот из запомненных, что рядом (сильнейший по
  сигналу). Адрес, который выдал роутер, сигнал и MAC моста — там же, строка
  «Роутер». Адрес роутер может сменить при следующем включении (15.11.2026: было
  .9, стало .6); для телефона его стоит закрепить в роутере по MAC. Роутер
  пропал — мост пробует снова сам, с паузами (5 с, 30 с, потом раз в 5 минут):
  пока он ищет сеть, тем, кто на K57, на секунду хуже.

Своя точка встаёт на канал роутера — радио у ESP32 одно; в момент входа в
роутер подключённые к K57 на секунду отпадают. Для живой ленты через роутер
нужен сигнал не слабее −65 дБм: 10.11.2026 при −65…−70 дБм терялась каждая
десятая датаграмма.

**Как открыть страницу, не зная адреса в роутере** (16.11.2026): по имени
**http://k57.local** — проверено в Edge на Windows и на iPhone; Android 12 и
новее тоже понимают такие имена. Ещё мост виден значком «K57 - WiFi-мост
прибора» в Проводнике Windows, раздел «Сеть» (`main/ssdp.c`), — если у сети
профиль «Частная». Закреплять адрес в роутере не нужно, и в сети заказчика
его роутер трогать не придётся. Через K57 адрес всегда 192.168.4.1. На
вкладке «Мост» первая строка — через какую сеть зашли вы и какой у вас адрес.

`sdkconfig.local` (в git не попадает): `CONFIG_K57_WIFI_SSID` и
`CONFIG_K57_WIFI_PASS` — роутер по умолчанию, пока со страницы не задан
другой; `CONFIG_K57_AP_ONLY=y` — по умолчанию роутера нет.

В Motor_Control путь выбирается явно (15.11.2026), в меню «Управление» —
галочка на одном из двух:

- **«Связь через WiFi (мост K57)»** — только своя сеть моста, 192.168.4.1. Если
  компьютер не в K57, Motor_Control подключает его туда сам.
- **«Связь через WiFi (роутер)»** — только через роутер. Мост Motor_Control
  ищет сам: спрашивает все сети компьютера широковещательно (UDP 5522,
  `K57_DISC_PORT`), и мост отвечает — адрес вписывать не нужно, даже если
  роутер его сменил. Не нашёлся — запасной адрес `host=` из `bin\Debug\link.ini`.
  На K57 сам не уходит и WiFi компьютера не трогает.

Ни одна галочка не стоит — связь через PCAN. В `link.ini` это `link=k57`,
`link=router` или `link=can`. В заголовке окна — сеть, через которую идёт
связь («через роутер …» или «K57 (точка моста)»), и адрес.

Проверить мост без Motor_Control:

```
python tools/net_test.py                 своя точка K57
python tools/net_test.py 192.168.1.50    мост в общей сети
```

## Консоль

Раз в секунду мост печатает в свой COM-порт (115200), сколько кадров каждого
номера пришло с прибора и что ушло в сеть. Команду прибору можно дать прямо из
монитора: `c <cmd> [d1] [d2] [d3]`, например `c 333` — прибор пришлёт строку с
версией прошивки. Ответы ACK печатаются там же.

## Чёрный ящик

Мост держит в памяти последние ~0,6 с быстрой ленты прибора и по аварии
сохраняет их во флеш — шесть последних записей (места по 128 кБ с 12.11.2026;
записи прежней раскладки, по 192 кБ, при переходе не читаются). Motor_Control
сам скачивает каждую новую в `SPL\spl_data\BlackBox`. В Motor_Control: «Измерения →
Чёрный ящик (WiFi-мост)…», запись сохраняется в .spl для Wscope. Пуск вручную
из консоли моста — `b`. Подробно — `docs/esp32-spi-protocol-RU.md`, «Чёрный
ящик».

Таблица разделов своя (`partitions.csv`, с 10.11.2026). Плату со старой
прошивкой надо прошить целиком (`idf.py flash` так и делает); без раздела
`bbox` мост работает, но чёрный ящик выключен — так и пишет в лог.

## Страница в браузере

С 12.11.2026 мост показывает прибор в браузере: сеть K57, адрес
**http://192.168.4.1** — с компьютера, телефона или планшета, без Motor_Control.
Страница — `main/page/index.html`, вшита в прошивку; данные — запросами
`/api/state`, `/api/errors`, `/api/journal`, `/api/bbox`, `/api/bridge`
(`main/web_page.c`). Описания кодов — вшитый при сборке `bin/ErrorCodes.h`.

- **Инвертор** — как панель «Однофазный инвертор» Motor_Control: ключи,
  разрешение сети, режим, Uref, F, Iзад и величины кадра 140 раз в 0,7 с. В
  шапке — состояние инвертора и круг: красный — есть текущая ошибка.
- **Таблицы** — все таблицы Motor_Control (`bin\Debug\CanTxFiles\*.ini`):
  калибровка АЦП, регуляторы, паспорт, GridTie, ЦАП… Вшиты при сборке; новые
  .ini Motor_Control отправляет сам — «Управление → Отправить таблицы в
  WiFi-мост», мост держит их во флеше (`main/tables.c`). Имена значений после
  шестого поля строки (как у `Src` в `ЦАП.ini`) — выпадающий список.
- **Ошибки**, **Журнал** (длинный журнал моста), **Чёрный ящик** (список;
  смотреть записи — в Motor_Control), **Прошивка** (прибора, через мост - ниже),
  **Мост** (версия, связь, обновление прошивки моста).

**Чей сеанс.** Сеанс Motor_Control открыт («Подключить») — страница только
показывает то, что идёт по нему. Сеанса нет (Motor_Control закрыт или в нём
«Отключить») — мост, пока страница открыта, раз в секунду шлёт прибору
команду **344 «только смотреть»**: кадр 140, лампа, список ошибок. Ключи и
уставки она не трогает — работающий инвертор от открытой страницы не встанет.
Сеанс мост узнаёт у самого прибора: бит 0 слова 2 кадра 140 (`sbit.connect`).

**Управление и таблицы** — только при закрытом сеансе Motor_Control и с паролем
(поле наверху вкладки «Инвертор», браузер его запоминает). Мост принимает не
сырые команды, а действия (`/api/ctl`, `live.c`) и команды таблиц (`/api/tbl`,
`tables.c`) — только из таблиц и только в их пределах Мин..Макс.

Для проверки страницы без настоящей неисправности: в Watch прибора
`dbgNvRaise = <код>` — поднять аварию один раз, `dbgErrBlink = <код>` — мигать
ею (3 с горит, 3 с нет; `dbgErrBlinkSec`), `0` — стоп.

## Прошивка прибора через мост

С 12.11.2026 прибор прошивается без PCAN и JTAG: вкладка «Прошивка» на
странице или в Motor_Control «Управление → Прошить прибор через WiFi-мост…»,
файл `INVERTOR_CCS\CPU1_FLASH\invertor.out`.

Два шага. Сначала из .out вырезается образ (около 0,1 МБ, формат - в
`main/fwup.h`), уходит в мост и проверяется - прибор работает как работал.
Потом мост сам прошивает прибор по SPI тем же протоколом, что CAN-загрузчик
(`INVERTOR_CCS/my_Files/Bootloader/CAN_Bootloader_Protocol.md`, «Канал SPI»):
WiFi для этого не нужен. Отказ - мост начинает заново сам, до трёх раз; образ
остаётся в мосте, повторить можно и потом. Калибровки (BANK4) не стираются.

Нужны пароль, закрытый сеанс Motor_Control и закрытые ключи. Питание прибора
во время прошивки не снимать. Прибор со старой прошивкой (до 12.11.2026)
по SPI в загрузчик не уходит - его один раз прошить по CAN или JTAG.

Образ лежит во втором месте под программу моста; следующее обновление моста
его сотрёт, и пока прибор прошивается, мост не обновляется.

## Сборка и прошивка

ESP-IDF v5.4. В PowerShell окружение поднимается скриптом установщика —
`export.ps1` из самого IDF без системного Python не работает:

```
. C:\Espressif\Initialize-Idf.ps1
cd ESP32_BRIDGE
idf.py build
idf.py -p COM<N> flash monitor
```

### По WiFi, без кабеля

С 12.11.2026 мост обновляется по сети. В Motor_Control: «Управление →
Обновить прошивку WiFi-моста…», файл — `build\esp32_bridge.bin`. Или из
командной строки:

```
curl -u k57:<пароль> --data-binary @build/esp32_bridge.bin http://192.168.4.1/update
```

Пароль — `CONFIG_K57_ADMIN_PASS` в `sdkconfig.local`; не задан — пароль сети
K57. Версия моста — `http://192.168.4.1/version`.

Новая прошивка пишется во второе место под программу и сначала считается
**пробной**: проработала 20 с — подтверждена; не подтвердилась за минуту
(зависла, не завела сеть) — мост перезапускается и возвращается к прежней.
Проверено на стенде: 889 кБ за 9 с; мусорный файл не принят
(`ESP_ERR_OTA_VALIDATE_FAILED`); прошивка без подтверждения через минуту
откатилась сама.

**Возврат к прежней — свойство загрузчика**, а загрузчик по WiFi не
обновляется. Плату со старым загрузчиком (до 12.11.2026) надо один раз прошить
по USB, `idf.py flash`.

### В VS Code

Нужно расширение Espressif IDF. Открывать **папку `ESP32_BRIDGE`**, а не весь
ESP57: расширение ищет `CMakeLists.txt` проекта в корне окна. Сборка, прошивка
и монитор — кнопками в нижней строке. Настройки `.vscode` (версия IDF, порт,
IntelliSense) локальные и в репозиторий не попадают. Подсказки по коду
появятся после первой сборки: пути берутся из `build/compile_commands.json`.

На этой же плате жила прошивка ESP_INV (`C:\Work\ESP_INV\firmware`).
Вернуть её — `idf.py -p COM<N> flash` из её каталога.
